# KilnCMS Unreleased — full release notes

The long-form entries behind the Unreleased section of
[CHANGELOG.md](../../CHANGELOG.md), as they were written when each change
merged. `CHANGELOG.md` carries the one-line summary of each; this file
carries the reasoning.

## Upgrade notes

<a id="reserved-route-slugs-upgrade"></a>

- **List the records a newly reserved route already shadowed (#2898).** Run `mix kiln.reserved_paths`, or in a release `bin/kiln_cms eval 'KilnCMS.Release.reserved_paths()'`. It lists every page whose slug, and every record whose path alias starts with, one of `developers`, `ready`, `setup`, `sign-in`, `sign-out`, `actor`, `ap`, `mcp`, `password-reset`, or the first segment of an installed plugin's public route. Those URLs were never served: the built-in route answered first. Nothing is renamed for you; give each a new slug or alias in the editor, and add a redirect if the old URL was ever linked. The records still read and save as before; only a change to the slug or alias is checked. No migration; the command is read-only.

<a id="session-bound-sockets-upgrade"></a>

- **Collab tokens minted before this release are accepted for this release only (#2490).** The collaborative editor's socket token now names the browser session it was minted for (`"j"`, the session's jti), so a per-session sign-out can close the room ([Security](#session-bound-sockets)). A token minted by a node on the previous release has no `"j"`. During and after a rolling deploy it is still accepted, with the per-account behavior it always had: no session check, closed only by per-account sign-outs or at its next reconnect. Each such connect logs "Collab socket connect with a legacy collab token (no session)" at `:info`. Tokens live 24 hours, so none is left a day after the last old node stops. A node on the previous release accepts the new tokens (it ignores `"j"`), so editors moving between old and new nodes keep their rooms.
  - **The next release is planned to refuse a token without `"j"`.** Upgrade through this release rather than past it: skipping it, editors with a page open across the upgrade would lose their collaborative room until they reload the page.
  - **No migration, no setting; rolling the pin back is safe.** An older release reads the new tokens as before and checks no session.

<a id="form-field-conditions-upgrade"></a>

- **Add form field conditions only once every node runs this release (#2262).** One expand-only migration adds a nullable jsonb column, `form_fields.condition`; nothing is backfilled, and a form without a condition behaves and renders as before.
  - **During a rolling deploy.** An older node does not know conditions: it renders every field, browser-required where **Required** is ticked, and enforces each field's own **Required** on submit. A page drawn by a new node can post to an old one, which then refuses a submission that left a required, hidden field blank. Wait until the deploy has finished before adding a condition to a required field.
  - **Before rolling back.** The previous release shows every conditional field and requires each one marked **Required** from every visitor. If that would ask visitors something they shouldn't be asked, untick **Required** on those fields first. The stored conditions are kept and apply again after the next upgrade.
  - **`FormField.field_type` is now a `KilnCMS.Types.KnownAtom`.** No migration (the column stays text). From this release on, a field whose type a newer release adds is skipped by every reader (public form, schema, submissions, CSV export columns, autoresponder, builder) instead of failing the form. Releases before this one still fail to load such a form, so the next new type, `page_break` for multi-page forms (#2266), ships no earlier than the next release ([New values in an atom column](../releasing.md#new-values-in-an-atom-column)).
  - See [Before you upgrade or roll back](../forms.md#before-you-upgrade-or-roll-back).

<a id="platform-notice-rollback"></a>

- **Before rolling back past this release, let every pending platform notice be delivered (#2811).** Turning off a platform alert kind now writes a platform notice ([Added](#platform-alert-off-notice)), a dispatch row on the new channel `platform_notice`. The previous release cannot load that row.
  - **During a rolling deploy.** A node still on the previous release fails the notice's delivery job; it is retried (up to 10 attempts per job, and the minute scheduler queues it again) until a node on this release delivers it. The notice is late, never sent to the wrong people.
  - **Rolling back.** A notice not yet delivered when the last new node stops fails every minute on the previous release until its one-day delivery window closes, and is then never sent. The `platform_alerts_changed` event in the instance security log is kept either way. To check that none is waiting, `SELECT count(*) FROM security_alert_dispatches WHERE channel = 'platform_notice' AND alert_sent_at IS NULL AND failed_at IS NULL;` should return `0`. A notice already delivered still shows after a rollback, with the inbox line "Security alerts were made quieter".
  - **No migration and no setting.** See [For operators](../security-alerts.md#for-operators).

<a id="backup-reports-upgrade"></a>

- **Platform admins start getting backup failure email by default (#2229).** From this release, every platform admin is emailed about a backup that failed, reached no off-site destination, or reached only some of its destinations: `User.notify_on_backup` defaults to `failures` for every existing account. Each admin can choose **Every run** or **Off** under **Your settings**, **Email notifications**, **Backup emails**; nobody can choose for them, platform admin included. See [Reports and alerts](../backups.md#reports-and-alerts-2229).
  - **Cron's backups are reported too.** A cron backup is reported when History imports it (when a platform admin opens Backups, after each in-app backup, and on each last-good marker sync, every 15 minutes by default), so its email can arrive up to one of those intervals late. Only runs that finished within 48 hours are reported, so the first import of a directory of old backups mails nothing about them.
  - **The bell rows are always written.** A failed or partly off-site backup puts a notice in every platform admin's bell whatever their email choice; the choice mutes the email only.
  - **During a rolling deploy.** A report job an old node picks up fails there and retries (20 attempts; about five days on the mail backoff), so it is delayed, not lost. A run an old node finishes gets no report, and no "recovered" email.
  - **Before rolling back**, let the `mail` queue drain of `KilnCMS.Backups.ReportWorker` and `KilnCMS.Backups.ReportMailWorker` jobs: the older release fails each until it is discarded. It then shows the two new bell events as generic notifications that link to the inbox, and ignores `users.notify_on_backup` and `backup_runs.last_failed_at`. The migration is expand-only (a defaulted not-null text column and a nullable timestamp), so rolling the pin back is otherwise safe. See [Rolling back past backup reports](../releasing.md#rolling-back-past-backup-reports).

<a id="scanner-guard-rule-source-upgrade"></a>

- **Automatic block rules from before the upgrade keep alerting until they expire (#2810).** One additive migration adds `ip_block_rules.source` (`NOT NULL DEFAULT 'admin'`), which records whether a rule was added by an admin or by the scanner guard, so that the scanner guard's refusals stop alerting ([Changed](#scanner-guard-refusals-no-alert)). Nothing is backfilled: a rule the scanner guard added before the upgrade, or added during a rolling deploy by a node still on the previous release, reads `admin`, and the requests it refuses raise `blocked_ip` until it expires (`KILN_SCANNER_BLOCKING_BLOCK_MINUTES`, 60 minutes by default, at most 7 days). To stop one sooner, **Remove** it on `/editor/ip-blocks` (its note is **Automatic: scanner 404s**). During the deploy, a node still on the previous release that sends a window's `blocked_ip` summary also counts the scanner guard's refusals in it.
  - **Rolling the pin back is safe.** The previous release ignores the column and alerts on every rule's refusals again; the column can stay. See [Running more than one server](../security-alerts.md#running-more-than-one-server).

<a id="crawler-claim-evidence-upgrade"></a>

- **DuckDuckBot claims outside DuckDuckGo's list move to `reason="not_listed"` in the crawler telemetry, and one new table records when the 404 guard first saw them (#2852).** A DuckDuckBot claim from an address outside DuckDuckGo's fresh published list is now `{:unverified, :not_listed}` rather than `{:unverified, :failed}` ([Security](#crawler-claim-evidence)).
  - **Dashboards and alerts.** The series `kiln_cms_delivery_unverified_crawler_count{engine="duckduckgo",reason="failed"}` stops growing and `{engine="duckduckgo",reason="not_listed"}` takes its place; for the other engines `failed` still means DNS proved the claim false. A query that read `reason="failed"` as "spoofed claims charged as `empty`" should read `reason=~"failed|not_listed"`. `kiln_cms_delivery_client_class_count` is unchanged: such a request is still charged as `class="empty"`. One new counter, `kiln_cms_crawler_verification_sighting_unavailable_count{reason}`, should stay at zero (see [Crawler verification](../observability.md#crawler-verification)).
  - **Migration.** One additive migration creates `crawler_sightings` (a hashed client key, the engine, the first sighting and an expiry; no address in the clear). Only the smart 404 guard writes it, so it stays empty unless `KILN_SCANNER_BLOCKING` and crawler verification are both on. An hourly cron job, `KilnCMS.Security.CrawlerSighting.Workers.Prune` on the `default` queue at minute 41, deletes rows idle for 48 hours. The staging scrub purges the table (`crawler_sightings_purged`).
  - **During a rolling deploy.** A node on the previous release counts a list-only DuckDuckBot claim at once and exempts IPv6 DuckDuckBot, as before. A node on this release that runs before the migration finds no table: it logs "Crawler sighting store unavailable (…)" at `:error`, at most once a minute, and leaves such claims exempt until the table exists.
  - **Rolling the pin back is safe.** The previous release ignores the table; it can stay, or be dropped by hand.

## Breaking

<a id="breached-password-strictest-admin-sites"></a>

- **A password is held to the strictest breached-password policy of every site its account administers (#2408).** Until now the policy came from the site the request came in on alone: an admin of site A, whose policy is **Block**, could change or reset their password on site B's host, where the policy is **Warn** or **Off**, and set a breached one. That closed the threat model's residual risk (2).
  - **What changes.** When an existing account's password is set (change password, reset by token, an existing account accepting an invitation with a password), the policy is the strictest of the request site's policy for the account's tier there and the policy of every site the account administers, ordered Off, then Warn, then Block. An administered site with no saved policy brings in the operator's default (`BREACHED_PASSWORD_POLICY`, `warn` if unset). "Administers" means an active membership that is admin there, a live temporary admin grant included; a platform admin administers every site; an erased account administers none. A site's own policy is still downgraded to Warn for an account that is not its admin, but an administered site's never is.
  - **Why under Breaking.** A site's **Off** used to mean that nothing about a password set on that site was sent to Have I Been Pwned while the setting could be read. That no longer holds for someone who also administers a site that checks: their password is looked up, and can be refused, on every host. The Password policy page says so under **Off**. `BREACHED_PASSWORD_CHECK=false` is still the only switch that guarantees no request.
  - **Unchanged.** A registration, the first-run setup and an invitation that creates a new account have no administered sites yet and are judged as before. Editors and viewers are never refused. The cross-site read is bounded (two queries for a member, at most three for a platform admin, whatever the number of sites), and a failure to read it fails open to Warn for its part of the answer, with one log line that names nobody.
  - **No migration; rolling the pin back is safe.** An older release goes back to the request site's policy alone. Why this rule and not another: [ADR 0085](../decisions/0085-an-administrators-password-answers-to-the-strictest-policy-of-every-site-they-administer-and-is-checked-at-sign-in-only-where-a-site-asks.md).

## Added

<a id="breached-password-sign-in-check"></a>

- **A site can check its administrators' passwords against known breaches when they sign in (#2407).** The breached-password check used to run only when a password was set, so a breached password set before the check shipped was never noticed. **Sign-in & access → Password policy** (`/editor/password-policy`) now has a checkbox, **Also check administrators' passwords when they sign in**, off by default. Saving it requires the site's admin role.
  - **Who is checked.** Only someone who administers a site with the box ticked, signing in with a password, on any site's host and through any door: the sign-in form, the form `POST` and `POST /api/auth/sign_in`. Editors and viewers are never checked at sign-in. A platform admin answers to every site with the box ticked. The outcome is the strictest policy among the administered sites that have the box ticked; a site with it unticked plays no part, and neither does the site the request came in on.
  - **Block.** The sign-in is refused before any session, remember-me cookie or second-factor prompt. The token the password minted is revoked, and a reset link is emailed: a mail of its own, "Choose a new password for your (site) account", saying that someone signed in with the account's current password and that it appears in a breach. The mail names a site whose policy refused the sign-in, so it names one the person administers rather than whichever host they used: the site the request came in on when it is one of them, otherwise the one with the smallest id, so the same one each time (#3436). A platform admin answers to every site, so their mail names the site the request came in on, or the default site with no request site. The browser lands on the password reset page (`/reset`) with "Your password appears in a known data breach, so it can't be used to sign in as an administrator. We've emailed you a link to choose a new one. If it doesn't arrive, request one below." The API answers `403` with `code: "password_reset_required"` and no token.
  - **Warn.** The sign-in goes ahead. A browser sign-in shows "Your password appears in a public data breach. Change it soon from your account page." once it completes, after the second factor where there is one. The API's `201` carries `"password_breach": {"status": "breached"}`: the one-step sign-in's, or for a two-factor administrator the `201` from `/api/auth/sign_in/verify` (#3435). The `200` `two_factor_required` step never carries it, because the caller has not proved the second factor yet. The verdict is decided at the password step, the only one with the password to look up, and rides inside the encrypted, single-use `pending_token`, never in a URL. That token always holds the flag, `1` when warned and `0` when not, so it is the same length either way and a pending token printed in a client's logs does not reveal which administrators use a breached password.
  - **Bounded.** One lookup per sign-in, made only after the password verified: a wrong password, an unknown address, a throttled or challenged attempt and the form's keystrokes make none. The lookup holds no database connection and gives up after 1.5 seconds (`config :kiln_cms, KilnCMS.Accounts.BreachedPassword, sign_in_deadline: 1_500`, in milliseconds; there is no environment variable). Every failure, of the lookup or of reading the settings, lets the sign-in through. The same five-character hash prefix is sent at every checked sign-in; nothing is cached.
  - **Limits worth knowing.** The reset mail is charged to the address's reset-mail budget (five an hour), so repeated blocked sign-ins can use up the owner's own reset requests for that hour. Someone else holding the breached password can spend that budget on purpose, through these sign-ins or the anonymous `/reset` form, after which a blocked sign-in sends no reset mail for the rest of the hour. A blocked sign-in is not forgiven by the per-account sign-in throttle, so an owner who keeps retrying is paused after 20 attempts in 15 minutes. The pause mail then says why (#3437). It does not draw on the reset-mail budget, so it reaches the owner even when that budget is spent; like the usual pause mail, at most one goes to an address every six hours. When every attempt the counter holds was a blocked sign-in, it reads "Sign-in to your (site) account is paused briefly after repeated attempts that used your current password, which appears in a known data breach, so administrators can't sign in with it any more. Choose a new password; this also lifts the pause:", followed by a bare `/reset` link and "If this wasn't you, someone else knows your password: change it now." When only some were, it says "Some of them used your current password…" and "The others did not complete a sign-in. If none of this was you, someone else knows your password: change it now." Both carry the subject "Sign-in paused on your (site) account: choose a new password", no unlock link, no IP address and no count. They have a six-hour window of their own, separate from the usual "Unusual sign-in activity" mail's, which a pause with no blocked sign-ins in it still gets, unchanged (#3470). Sharing one window let a pause of wrong guesses spend it, so a later pause of blocked sign-ins, the stronger news, mailed nothing for six hours. An address therefore gets at most one of each mail every six hours, and only someone holding the correct password of an administrator whose site blocks it can trigger the breached one. When either mail fails to be queued, its window is handed back so the next pause can try again. One case still mails nothing: someone who has spent the address's reset mails and then makes too few blocked attempts to pause the account (20 in 15 minutes) leaves the owner with neither a reset mail nor a pause mail. The throttle itself is unchanged: who is admitted, the budget and the window are as before. A `403` `password_reset_required` tells the caller that the password was right and that the account administers a site that checks; it issues no token.
  - **For operators.** The audit log records each refusal as `sign_in_failed` with `method: "password"` and `reason: "breached_password"`, unsampled, in the log of each site whose policy refused it (not the site the request came in on), and does not count it toward the failed-sign-ins alert. When those sites cannot be read, which can happen only for a platform admin, the refusal still stands and is recorded once in the log of the site the request came in on instead, with the same type and reason, unsampled and not counted toward the alert (#3438). That event names no other site, and the account appears unlabelled unless it is a member of that site. A sign-in with no request site (no HTTP door) records nothing, like every other sign-in event. `[:kiln_cms, :password, :breach_check]` gains `action: :sign_in`. The Security posture line `core.breached_passwords` gains a `sign_in_check` fact; its status is unchanged.
  - **Upgrade.** One expand-only migration adds `site_password_policy.check_on_sign_in` (boolean, not null, default false). Rolling the pin back is safe: an older release ignores the column. During a rolling deploy an older node does not show the sign-in warning that a newer node left for it; the older "breached password" note after a register or reset still works across both. A `pending_token` minted by an older node made no lookup and reads as not warned when a newer node redeems it, and an older node redeeming a newer one ignores the flag, so a two-factor API sign-in that crosses nodes can miss the warning, never fail. The breached-pause mail's own window needs no migration: it is a new row in the existing sign-in throttle store, which an older release ignores.

<a id="form-field-conditions"></a>

- **A form field can be shown or hidden based on earlier answers (#2262).** Admins build it in the form builder: click a field, then **Conditional logic** → **Add a condition**, choose **Show this field** or **Hide this field**, and one or more tests of earlier fields joined by **all of these match** or **any of these match**. The guide is [Show or hide a field based on an earlier answer](../forms.md#show-or-hide-a-field-based-on-an-earlier-answer).
  - **The model.** `FormField.condition` is an embedded `KilnCMS.CMS.FormFieldCondition`: `action` (`:show` or `:hide`) and a `rule` in the `KilnCMS.CMS.Conditions` shape custom fields already use. A rule names only fields strictly earlier in the form, so nothing can loop. `KilnCMS.Forms.Logic` evaluates the fields in form order, and a field its condition hides has no value for later rules, so conditions chain. A condition this release can't apply (it names a field that is gone or not earlier, or has an action this release doesn't know) leaves its field shown. The checks on write are `KilnCMS.CMS.Validations.FormFieldCondition`'s, on the resource: a delete, a move to another form, a retype or a reorder that would break another field's condition is refused, and a rename rewrites the conditions that name the field (`KilnCMS.CMS.Changes.RewriteConditionReferences`).
  - **Why not `visible_when`.** The rule engine has no "not", so a hide rule stored as a negated show rule could not be read back as the rule the admin wrote; the separate `action` keeps the intent. An unknown action fails visible.
  - **The server decides.** `KilnCMS.Forms.submit/3` evaluates every condition again from what was sent. A hidden field is never required, and its value is dropped before storage, the spam checks, the notification and autoresponder mails and the `form.submitted` webhook, which closes smuggling data through a field the visitor was never asked.
  - **Rendering.** Only a form with a condition carries anything new: `data-kiln-enhance` on the form, `data-kiln-field` / `data-kiln-condition` on its field wrappers, and a `<script type="module">` for `/assets/js/challenge_static.js`, which now also carries the form script (`assets/js/form_enhance.js`; about 10.5 KB minified, from 4.6 KB). `public.js` is unchanged, and a form with no condition renders byte for byte as before. Without JavaScript every field is shown, a conditional field carries the note "Depends on an earlier answer; leave it blank if it doesn't apply." and no browser `required`, and the server applies the rules. LiveView previews show every field.
  - **Headless.** `GET /api/forms/:slug` gives each field a `condition`: `null`, or `{"action": "show" | "hide", "rule": ...}`, `null` for one the server can't apply. A JSON submission's answer lists under `discarded` the fields whose sent values were dropped because their condition hid them, only when there are any. A front end that doesn't evaluate conditions therefore still gets `ok: true` while losing those values. The JavaScript client's types gain `FormField.condition` and `FormSubmitResult.discarded`; the Elixir client documents both. See [Embeddable forms](../api.md#embeddable-forms).
  - **Condition values are public.** They are in the page's HTML and the schema, so they must not hold a secret.
  - **Upgrade.** See [the upgrade note](#form-field-conditions-upgrade).

<a id="backup-log-viewer"></a>

- **A backup's log can be read and downloaded from the Backups page (part of #2230, #2231).** Every run has stored a log of up to 200 lines since #2217, but nothing showed it: History shows a run's outcome and error, not the step sequence, the `pg_dump` and rclone lines or what retention removed on each destination. The Backups page gains a **Log** tab (`/editor/backups/log`), and each History row a **View log** link to it. The guide is [Read and download the log of a backup](../backups.md#read-and-download-the-log-of-a-backup).
  - **What the tab shows.** One backup at a time, chosen in **Backup** (the newest 25, plus an older one opened through `?run=<id>`); with none named, the one holding the backup lock, else the newest. A summary card (stamp, status, trigger, components, start and finish, the run's error), then each line with its time, level and step. **All**, **Warnings and errors** and **Errors** filter it (`?level=warn`, `?level=error`). Where lines were dropped to keep a log at 200, a marker such as "37 lines were dropped to keep the log small" is shown at every level, with the count the download's `truncated` line gives (#3490). A log capped again after a resume or re-send added to it counts the lines its earlier cap dropped too (`KilnCMS.Backups.Log.marker_count/1`), so the count is every line the run's log has lost. A cron backup carries only what the importer recorded, and says its full output is in the host's cron log.
  - **While a backup runs.** Lines arrive at step boundaries, when a step writes the run, not as a step works. The page reads the run again every 3 seconds while it runs and stops when it finishes; after an hour it stops and says "This page stopped checking for new lines. Reload it to follow the backup again." A step's write also prompts a re-read on clustered nodes ([live progress](#backup-live-progress)).
  - **Redacted again.** Each message, step name, trigger and error is redacted again whenever it is shown or downloaded, with the `DATABASE_URL` password and the process's secret variables known now as well as `KilnCMS.Backups.Redact`'s patterns, so a secret set later, or a new pattern, applies to old lines. Destination credentials are removed by pattern only. Control characters, C1 controls and bidirectional overrides become U+FFFD, so the file is safe to `cat`. `KilnCMS.Backups.LogText` does this for both the page and the file.
  - **The download.** **Download log** is `GET /editor/backups/runs/:id/log.txt`: a `text/plain` attachment, `kiln-backup-log-<stamp>.txt`, never cached, with `#` header lines about the run and then `<ISO 8601> <LEVEL> <step> <message>`, every level, continuation lines indented. It answers `403` `admin_required`, `403` `console_shares_origin`, `403` `cross_site_request` (a browser's `Sec-Fetch-Site` other than `same-origin` or `none`, or `Sec-Fetch-Dest` other than `document` or `empty`; requests without those headers pass), `404` `not_found` (a malformed id, an unknown run or a refused read), and `429` once the `:export` budget (10 a minute per account, per node, shared with backup file downloads and the content-list and security-log exports) is spent, in that order. Only a run that is found is charged, so a `403` or a `404` spends nothing (#3490): run ids are random UUIDs, so guessing them never paid, and the budget rations downloads, not typos. A `403` answers the same whether the id is a run's. Each download is logged at info (`backup log download user_id=… run_id=… stamp=… entries=…`); it writes no instance security event.
  - **Refused while the console shares an origin.** A log names destinations, hosts, paths and timings across every organization's backups, so with `KILN_CONSOLE_HOST` unset and more than one organization, or while the count can't be told, the tab shows a note and no backup, and the download is refused, under the same rule as backup file downloads. History itself is not hidden by this change ([threat model](../threat-model.md), residual risk 16).
  - **Upgrade.** No migration and no setting; rolling the pin back is safe. During a rolling deploy a request that reaches an older node finds no Log tab or download route and answers `404`. Why it works this way: [ADR 0092](../decisions/0092-a-backup-runs-log-is-shown-and-downloaded-redacted-refused-while-the-console-shares-an-origin-without-an-audit-event.md).

<a id="backup-live-progress"></a>

- **A running backup's progress reaches the Backups page and the Log tab about half a second after it is recorded, with an approximate percent on the strip (#3489, completes #2230).** Both pages read a running backup from the database every 3 seconds, and an idle Backups page read nothing, so a backup started by a schedule or another admin appeared only after a reload. The guide is [Follow a running backup](../backups.md#follow-a-running-backup).
  - **What changes on the page.** The strip under **Back up now** gains a bar (`role="progressbar"`, labelled "Backup progress", "About N% done"). It goes by steps: each step of a fresh backup after `start` is an equal seventh, the media parts split theirs when the node knows how many there are, and a re-send goes by destinations. It never reads 100 and is not shown while a resume waits to start. A page with an empty strip, or one whose hour of polling ran out, picks up a backup again on a clustered node, and a Log tab that had stopped checking starts again.
  - **A nudge, not a source.** Every write to the backup lock, every run write the step recorder makes and the end of each backup sends `{:kiln_backup_progress, 1, payload}` on the `Phoenix.PubSub` topic `"backups:progress"` (`KilnCMS.Backups.Progress`), after its transaction commits; a rolled-back write sends nothing. A page that hears one about its backup re-reads the database at most once every 500 ms, and never arms a second poll timer. The 3-second poll stays the source of truth and the fallback, because a message reaches only nodes clustered with the sender. Poll-only: the lock changes a Cancel makes (the backup's end is announced instead), run writes outside a step (imports, the canceled run's own status, retention marking older runs pruned), and every change on an unclustered node. Restore sends nothing.
  - **The payload.** Exactly `chain`, `stamp`, `run`, `step`, `part`, `phase` and `percent`: ids, the lock's own step and phase values, counts. Never log text, an error, a path or file name (a path can carry personal data), env or destination config. A consumer ignores a version it doesn't know.
  - **Who sees it.** Platform admins only: only a page that admits them subscribes, and each message and each re-read checks again, so an admin demoted while the page is open gets nothing new. The Log tab applies the console-origin refusal at every re-read.
  - **Upgrade.** No migration and no setting; rolling the pin back is safe. During a rolling deploy an older node sends no messages, and pages on any node keep following the backup through the poll.

<a id="api-key-rate-limit-more-buckets"></a>

- **Four more rate limits raise the platform's `api_key_rate_limited` alert for a verified API key: `media_render`, `preview_api`, `unlock` and `feed_join` (#2809).** Until now only `api`, `gql`, `media_upload`, `media_transform` and `plugin_endpoint` did, so a key over the image-render budget, the preview-token read budget, the passphrase-unlock budget or the change feed's connect budget raised nothing.
  - **Where each is charged.** `preview_api`: a headless read that presents a preview token (`/api/json`, `GET /api/content/:type/:slug`, `GET /api/visual-editing/:type/:slug`). `unlock`: `POST /api/content/:type/:slug/unlock` and the lock page's `POST /_unlock`. `media_render`: an image transform that has to render (a cache miss on `/media/:id/t/...`). `feed_join`: a connect to `GET /api/feed`.
  - **What a client sees is unchanged.** A refused feed connect is still the stream's `200` with `event: busy`, not a `429`; the others are `429` as before.
  - **Which keys count.** `preview_api` and `/api/content/.../unlock` run after the `/api` pipeline checked the key, so a forged or revoked key is answered `401` first and records nothing. `/_unlock`, `media_render` and `feed_join` run before any key is checked and alert only for a key this server verified in the last 2.5 to 5 minutes, as transforms and plugin routes already do ([ADR 0053](../decisions/0053-rate-limit-alerts-trust-a-node-local-verified-key-cache-never-a-check-on-the-refusal-path.md), amended).
  - **Left out on purpose.** The `docs` limit (the API explorer and schema downloads) raises nothing, by owner decision.
  - **For operators.** The event's `bucket` and the `kiln_cms.security.api_key_trip.count` counter's `bucket` tag gain the four values. No migration; rolling the pin back is safe. See [API keys over a rate limit](../security-alerts.md#api-keys-over-a-rate-limit).
  - **For developers.** `KilnCMS.Security.ApiKeyTrip.buckets/0` lists the four. `KilnCMSWeb.MediaTransformController` and `KilnCMSWeb.FeedStream.JoinBudget` check their limit with `KilnCMSWeb.RateLimit.check/2` rather than the plug, so each calls `ApiKeyTrip.note/2` itself.

<a id="platform-alert-off-notice"></a>

- **Turning off a platform security alert now sends every platform admin a notice, by bell and email (#2811).** A platform admin unticking **API keys over a rate limit** under **Platform alerts** on **Security alerts** (`/editor/security-alerts`) used to be recorded only in the instance security log, so a hijacked platform admin session could quiet the alert without anyone hearing. A site's alerts have always been turned down with a notice; the platform's now are too. The guide is [Turn off rate-limit alerts for API keys](../security-alerts.md#turn-off-rate-limit-alerts-for-api-keys).
  - **Who hears it.** Every platform admin as they are at delivery, a live temporary platform grant included and erased accounts excluded, and the one who saved included. The bell row is in the default site, headed "Security alerts were turned down" with the line "Some platform security alerts were turned off", and is counted in other sites' "unread platform alerts" entry. The email's subject is "Platform security alerts were changed"; it lists what was turned off and links to the Security alerts page.
  - **No way to quiet it.** No setting turns it off and no mute applies. It is never grouped and has no summary, and no webhook carries it.
  - **Fails closed.** The notice is written in the save's transaction, with the `platform_alerts_changed` event. If it cannot be written, the save fails, nothing changes and the page says "The platform alert settings could not be saved."
  - **What the page says.** The section's line now ends "…and every platform admin is sent a notice." A save that turned a kind off says "Platform alert settings saved. Every platform admin will be sent a notice." That is decided from the row the save locked, so a page loaded before another admin's save neither promises a notice it did not write nor sends a second. Turning the kind back on, or saving unchanged, sends nothing.
  - **For developers.** New `KilnCMS.Security.AlertGate.insert_platform_notice!/1`, `KilnCMS.Security.Alerts.platform_notice_changes/0` (today `platform_kind_disabled`) and `KilnCMS.Security.Changes.NoticePlatformAlertSettings`; `AlertDispatch.channel` gains `:platform_notice`. A saved `PlatformAlertSettings` record's `__metadata__.platform_notice?` says whether the save wrote one. [ADR 0027](../decisions/0027-security-alerts-derive-from-the-audit-log-and-turning-a-sites-alerts-down-is-never-silent.md) is amended.
  - **Upgrade.** No migration. Rolling deploys delay the notice and a rollback can lose one still pending: see [the upgrade note](#platform-notice-rollback).

<a id="backup-reports"></a>

- **A report after each backup: email to the platform admins who want it, and a bell notice for each one that went wrong (part A of #2229).** Until now a failed backup was silent unless someone opened the Backups page. The guide is [Reports and alerts](../backups.md#reports-and-alerts-2229); the reasoning is [ADR 0094](../decisions/0094-a-backup-report-is-enqueued-in-the-runs-terminal-write.md). A ping URL per schedule (part B) and when each destination was last reached (part C) are still to come.
  - **Who gets what.** Only platform admins, since a backup covers every site. A failed backup (including one written here that reached no off-site destination) and a partly off-site one put "A backup failed" or "A backup reached only some destinations" in every platform admin's bell, linking to **Backups**; while it is unread, the next one replaces its line instead of adding a row, and opening Backups marks it read. In another site's console the bell counts them with the platform alerts. The email follows **Your settings** → **Email notifications** → **Backup emails**: **Failures only** (the default: failed and partly off-site), **Every run** (succeeded, skipped and canceled too) or **Off**. The choice is the account holder's alone (`User.notify_on_backup`, held by `Validations.OwnSecurityAlertMute`), and only platform admins see it.
  - **Recovered.** A failed backup that is resumed and then succeeds sends "Backup recovered" to everyone who was emailed the failure, and to whoever its class reaches by setting, and marks their unread failure notice about it read. A cron backup that was recorded as Interrupted and turns out to have finished sends "Backup finished after all". `Run.last_failed_at` (new, set only by the outcome write) is what remembers the failure across the resume.
  - **Cron backups.** Reported once History imports them, if they finished within 48 hours. Of several imported successes, only the newest is reported; failed, partly off-site and recovered cron backups always are.
  - **What it says.** English, through the instance relay. The stamp, schedules or trigger, times, components, sizes, whether every file verified, each destination's label and outcome, and up to five error lines from the run and five from its log, with links to the run and its log. Text from the run has its credentials redacted again and control characters replaced; an error line can still name a path or a host. It never includes destination keys, file paths, checksums, or anyone's name or address. The subject is always one line.
  - **How it is sent.** Each write that gives a run its outcome (`:finish`, `:fail`, `:skip`, `:cancel`, `:cancel_resume`, `:note_resume_refused`, `:import`, `:reevaluate_interrupted`) inserts a `KilnCMS.Backups.ReportWorker` job in its own transaction (`Run.Changes.AfterOutcome`), so the report and the outcome commit or fail together. That job writes the bell rows and queues one `KilnCMS.Backups.ReportMailWorker` job per admin, unique on the run, its `finished_at` and the recipient. Both carry ids only and read the run, recipient and address when they run; the mail job re-checks that the recipient is still a platform admin, still wants it and is not suppressed. A failed run's report waits a minute, so an interrupted run's log is recorded first. A failure to queue the report logs `Backup report of <stamp> not enqueued` and emits `[:kiln_cms, :backups, :report, :not_enqueued]`.
  - **Not reported.** A re-send: it is not a run, and a partly off-site notice stays as it was. A backup that never starts: keep `BACKUP_PING_URL` set.
  - **API.** `Backups.Run` and the notification preferences have no API exposure; nothing changes in JSON:API, GraphQL or MCP. `Notification` gains a system-only `:refresh` action and the events `:backup_failed` and `:backup_partly_offsite`.
  - **Upgrade.** See [the upgrade note](#backup-reports-upgrade).

<a id="backup-destination-freshness"></a>

- **The backup alarm names a destination no backup has reached within its threshold, on the Backups panel, the Overview strip and the Schedule tab (part of #2229).** A fresh last backup could hide a destination that had stopped receiving them: a schedule that no longer covered it, a remote that failed every night while another succeeded, a destination added and never sent to. The off-site line speaks only of the newest in-app backup. The status now asks, of every destination configured now, when a backup last reached it, and says "No backup has reached NAS in 26 hours.", "No backup has reached NAS in the last 8 days." or "No media backup has reached NAS in 26 hours." in the alarm's red, beside the off-site line. Platform admins only. The guide is [Check that each destination is still reached](../backups.md#check-that-each-destination-is-still-reached).
  - **What counts.** Each component this deployment backs up is judged against its own threshold (`stale_after_hours`, from its schedule or `BACKUP_STALE_AFTER_HOURS`), so a fresh database does not cover late media. Only `Succeeded` runs count, measured by the run's start (a re-send counts as data of its own time), with a verified file of that component: an in-app run through its `ok` entry for the destination, a cron run through its files' `destinations`. Failed, canceled and skipped runs never count.
  - **Exemptions.** `BACKUP_RCLONE_REMOTE` is exempt until any run of any age, the app's or cron's, has tried it; while nothing in the lookback has, each status read probes the whole history (one `EXISTS` query no index serves). A stored destination gets a grace period of each component's threshold from when it was created; one disabled and enabled again keeps its first creation time and alarms at once. Which env destination there is follows the environment of the node serving the page.
  - **The read.** One query through the `started_at` index: eight days, or the longest threshold when that is longer, at most 31 days and the newest 2000 runs. When the 2000-run cap cuts the read short of a threshold, a component it saw no backup of is not listed (it fails open). No migration.
  - **A cron-only media deployment.** Cron sends only to `BACKUP_RCLONE_REMOTE`. Where the in-app schedules are database-only and cron takes the media, a stored destination's media alarms indefinitely, because it holds none. Have an in-app schedule cover the media, or disable the destination.
  - **For developers and operators.** `KilnCMS.Backups.status/0` gains the additive key `destinations_stale`, each entry with `key`, `label`, `components`, `last_at`, `hours` and `lookback_days`; `KilnCMSWeb.BackupComponents.freshness_lines/1` renders it. A new event, `[:kiln_cms, :backups, :status, :destination_freshness_unreadable]`, carries `error` and `read` (`:runs`, `:env_probe` or `:grace`). `[:kiln_cms, :backups, :status, :destinations_unreadable]` now fires on every status read while the destinations table can't be read, not only when a partly off-site alarm needed it.
  - **Upgrade.** No migration and no setting; rolling the pin back is safe. An older node's pages show no freshness line.

<a id="bot-classes-regional-engines"></a>

- **More crawlers land in the bot-budget class they belong to (#2468).** `KilnCMS.BotClass` gave a browser-shaped crawler that was not on its lists the browser ceiling, and regional search engines the other-bot one, so raising **Search engines (%)** did nothing for them. See [How a request is classified](../bot-budgets.md#how-a-request-is-classified).
  - **Search engine, checked by DNS.** `SeznamBot` (PTR under `seznam.cz`) and `MojeekBot` (`mojeek.com`), each the domain the vendor documents, and Google Shopping's `Storebot-Google`, verified like Googlebot. A claim proven false is charged as No user agent, as for the others. Their published IP lists are not fetched yet.
  - **Other bot.** `GoogleOther` (Google's generic fetcher, no product), `AdsBot-Google` (checked only under `google.com`, which verification refuses; its landing-page checks now get the other-bot ceiling, 50% by default, instead of the browser's), and Naver's `Yeti` and Sogou's spiders: they document no domain to check, and an unprovable claim would keep the 404 guard's exemption for anyone who typed the name. `Qwantbot` is named here too: it can become a search engine once its verification domain is confirmed from Qwant's own documentation, since a wrong domain would prove the real crawler's claims false. A user agent with `compatible;` followed by a name ending in bot, crawler, spider or scraper is another bot even inside a browser's string; a phone model such as `CUBOT_X30` is not.
  - **AI crawler.** `Google-CloudVertexBot`, which fetches for Vertex AI Agents. AI crawlers keep the browser's 100% by default, so this raises its ceiling from 50%, no more than a browser user agent already gets.
  - **No migration; rolling the pin back is safe.** Telemetry's `engine` tag gains `:seznam` and `:mojeek`.

<a id="autoresponder-first-filled-email"></a>

- **The autoresponder confirms to the first email field the submission filled in (#2262).** `KilnCMS.Forms.Autoresponder.eligible?/3` used to take the form's first `:email` field and send nothing when that one was blank, even if a later email field held an address. It now takes the first `:email` field, in form order, with a non-blank value. That is needed for conditions, where the first email field may be hidden, and it changes forms without any condition too: a form with an optional first email field and a filled-in second one now sends a confirmation to the second. A `[field:<name>]` token for a field its condition hid expands to nothing, like a blank field; the **Confirmations** tab says so on a form with a condition. No migration; rolling the pin back restores the old choice.

<a id="sftp-prune-test-hint"></a>

- **The Destinations tab says when pressing Test on both SFTP destinations would let them prune (#3428).** Two SFTP destinations whose folders nest stay **Not pruned** until both trust host keys of the same type that differ and each has passed a Test since the later trust (#3200). When the Tests are all that's missing, each row now shows **Press Test on both destinations to let them prune.** with a link to [Let two SFTP destinations on different servers both prune](../backups.md#let-two-sftp-destinations-on-different-servers-both-prune).
  - **When it shows.** On an enabled row with retention ticked whose block a Test would clear for every overlapping SFTP row (`KilnCMS.Backups.Retention.cleared_by_test?/3`, which reuses the pruning rule rather than restating it). A partner with no trusted key, a key of another type or the same fingerprint means no hint, since testing can't clear it.
  - **No migration; rolling the pin back is safe.** Pruning itself is unchanged.

<a id="sftp-path-spaces"></a>

- **An SFTP destination's path may hold spaces and `+ @ ,` (#3199).** NAS shares are often named with a space (`/volume1/Backup Share`), and the path was held to the characters an S3 prefix allows, `A-Z a-z 0-9 . _ -`, so such a share could not be used at all.
  - **What changes.** Each folder name in **Path** may also hold the space, `+`, `@` and `,`. The path goes to the server as one length-prefixed SFTP string, never through a shell, so the characters that separate folders or climb out of them are all that could do harm, and those are still refused: `.` or `..` as a folder, `~`, `\`, NUL and control characters, and anything outside ASCII. A folder name may not start or end with a space (`/backups /kiln`): it would not read back the way it was typed, and it would let the stored path and the parsed one disagree. The form's help now gives `/volume1/Backup Share/kiln` as an example, and a refused path says "the path must be folder names of letters, digits, spaces and . _ - + @ , separated by /" or "the path must not have a space at the start or end of a folder name".
  - **Unchanged.** An S3 destination's prefix takes the same characters as before. An existing SFTP destination's stored path and location are untouched, so its recorded sends and resume checkpoints still match it.
  - **No migration; rolling the pin back is safe** as long as no SFTP destination has been saved with a new character in its path. An older release refuses to save such a destination again and refuses its path when it connects, so its backups fail until the path is changed. See [What a path may hold](../backups.md#what-an-sftp-path-may-hold).

<a id="sftp-distinct-servers-prune"></a>

- **Two SFTP destinations whose folders nest both prune once Kiln can prove they are different servers (#3200).** Since #2222, a pair of SFTP destinations with one path inside or around the other blocked retention on both, whatever host, port or login they named, because one server answers to many names. Two NAS boxes that both keep backups in `/backups` were never pruned.
  - **The rule.** `KilnCMS.Backups.Retention.prune_blocker/3` now lets such a pair prune when both rows trust a host key of the same type (both `ssh-ed25519`, say), the fingerprints differ, and each row's last Test passed after the later of the two keys' trusted times. A Test connects only to a server that offers the row's trusted key, so a passed Test shows that key is still that server's own once both were in place. Everything else stays blocked: a row with no trusted key, keys of different types (one server holds an ed25519 key and an RSA key), one fingerprint on both (one server reached by name and by IP), a failed Test, or a Test older than the other row's trust (a disabled row's server could have been reinstalled with the other's key since). The exact overlap, same host, port and login, is never lifted. The proof is positive only: nothing is inferred from a connection that wasn't refused.
  - **What to do.** On **Backups → Destinations**, check both rows trust keys of the same type, then press **Test** on each. Both rows then show **Prunes its old backups**. The **Not pruned:** text and the run log's skip line now say what would tell the two apart: "… the app can't tell whether it is the same server until both trust host keys of the same type that differ, and each has passed a Test since the later of the two was trusted". Steps are in [Let two SFTP destinations on different servers both prune](../backups.md#let-two-sftp-destinations-on-different-servers-both-prune).
  - **What it can't see.** A key that changes after both rows are proven is not noticed until the next Test or trust: a backup that meets the new key fails the destination before anything is sent or deleted, but does not count as a failed Test. A Test that started before the other row's re-trust and passed after it counts (a Test takes at most 30 seconds). Two SSH daemons with different keys in front of one disk, or a high-availability pair with a key per node, look like two servers. An SFTP destination still can't be compared with an S3, rclone or directory destination, or with `BACKUP_RCLONE_REMOTE`. In each case retention still deletes only what this installation's backup directory sent there ([ADR 0064](../decisions/0064-retention-on-a-backup-destination-deletes-only-what-this-installation-sent-there.md)), so the worst outcome is this installation's own backups kept for less time than its schedules ask. The rule and these limits are recorded in [ADR 0079](../decisions/0079-an-sftp-destinations-host-key-is-trusted-once-by-a-platform-admin-and-a-changed-key-fails-the-destination.md), "When to revisit".
  - **No migration; rolling the pin back is safe.** An older release blocks the pair again.

<a id="backup-cli"></a>

- **Backups have a command line: `bin/backup` in a release, `mix kiln.backup.*` in a checkout (part of #2234).** What the Backups page does used to be reachable from a shell only as hand-typed Elixir through `bin/kiln_cms rpc`, with no stable output. The guide is [Backups from the command line](../backup-cli.md).
  - **Commands.** `list [--limit N]` shows the newest backups in History and whether each one's files are on this host. `run [--components db,media] [--wait [--timeout SECONDS]]` asks for a backup as the Backups page does (trigger `console`); `--wait` follows it, 3 hours by default and 24 at most, and stopping the wait doesn't stop the backup. `verify <stamp|id>` re-checks a backup's files here: names, digests and sizes, the sidecar, and `pg_restore --list` for a dump. `prune` reports what retention would delete and each destination's pruning state. `rescan` imports cron-made backups in this host's backup directory, clearing the import backoff first. Each takes `--json`: one object with `schema`, `command`, `ok`, `exit_code` and `error`, plus the command's own keys, which are only ever added (those of `prune` and `rescan` are provisional and will gain keys). Exit `0` is success, `1` a failed command, `2` a usage error.
  - **Where each runs.** `list` and `verify` run beside the serving node through `bin/kiln_cms eval`, starting only the database connection: `verify` hashes gigabytes, which must not happen on the serving VM, and `list` works while the application is down. `run`, `rescan` and `prune` run inside it through `bin/kiln_cms rpc`, because they need its job queue and its importer state. Arguments reach the release base64-encoded, never as part of an Elixir expression. In Docker: `docker compose exec app bin/backup list`. `bin/backup` is POSIX `sh`, for the Linux release.
  - **`prune` deletes nothing.** It is the retention dry run. A real prune runs inside every backup, fenced by that backup's lease, so `bin/backup run` is how to prune now. Like every retention pass it imports cron-made backups into History first, and a report that can't be made logs "Backup retention skipped" and counts in `kiln_cms_backups_retention_skipped_count`, so that alert fires for a failed `bin/backup prune` too.
  - **`verify` records nothing.** It never sets a backup's verified flag (ADR 0033), and it is not a pass when nothing was here to hash (`nothing_local`), when the backup is still being written (`in_progress`) or when the backup lock can't be read (`lock_unreadable`). It is stricter than `scripts/backup.sh verify`, which remains the tool when the database is down: a recorded digest with no sidecar fails here.
  - **Mix tasks.** `mix kiln.backup.list`, `.run`, `.verify`, `.prune` and `.rescan` start the application with no job queue and no backup heartbeat, so a checkout pointed at a deployment's database never works off its jobs; a checkout's `run` only asks for the backup, and the serving application runs it.
  - **Not yet.** Destination rescan (#2225), listing what would be pruned on a destination, `restore` (#2226) and `unlock` (#2239).
  - **Upgrade.** A new image only: nothing to migrate or configure, and rolling the pin back is safe (the older image has no `bin/backup`). The exit codes rely on how Elixir 1.20's Kernel.CLI carries an exit out of `eval` and `rpc`; canary tests fail CI if a toolchain bump changes it. Why the commands are split this way and why `prune` only reports: [ADR 0088](../decisions/0088-the-backup-command-line-reads-beside-the-node-and-writes-inside-it-and-prunes-only-inside-a-backup.md).

<a id="backup-download"></a>

- **A platform admin can download a backup's local files from History (part of #2225).** Until now a backup left the server only through a shell (`scp`, `rsync`) or a destination's own tools. On **Backups → History**, a row whose files are on this server has a **Download** menu listing each file with its size (the dump, the archive or each part of a media set) and each component's **Checksum file**; a click starts the download and the page stays open. The guide is [Download the files of a backup](../backups.md#download-the-files-of-a-backup).
  - **Who and how it is recorded.** Platform admins only, re-checked at the click and again at the request; org admins, the `:backups` system actor and everyone else are refused (`Backups.Run` `:check_download` and `:download`, both `PlatformAdmin` only). Each download request writes `backup_downloaded` to the instance security log (`stamp`, `file`, `kind`, `bytes`, `node`; target `backup_run`) before any byte is sent; if it can't be written the answer is `503` `audit_failed` and nothing is sent. The click itself records nothing. The event raises no security alert.
  - **The link.** Minted on click, good for one minute, for this admin in this browser session only, and posted in a hidden CSRF-protected form to `POST /editor/backups/download`, so it never appears in a URL and the request log shows `[FILTERED]`. It is not single-use: a second request with it in that minute, from that session, is checked, charged and recorded again. `GET` and `HEAD` answer `405`.
  - **What is served.** Only names recorded on the row, compared byte for byte, and only regular files (no symlinks) in this server's `BACKUP_DIR`: never `.partial` files, markers, `manifest.json`, files retention marked pruned, or destination copies. Not while the backup is being written. One file per click, no archive of a set, no resume (no `Range`). Downloads share the `:export` budget with content-list and security-log exports: 10 a minute per account, per node, so a set of many parts downloads in batches. The file is checked again right before it is sent; one that changed or went in that moment answers `404` with nothing sent, after its event was written, and a server-log warning says so.
  - **Refused while the console shares an origin.** With `KILN_CONSOLE_HOST` unset and more than one organization, or while the organization count can't be told, downloads are off and the page says so in place of every Download menu: a site's injected code would otherwise be one request away from a full dump in a platform admin's browser. Set `KILN_CONSOLE_HOST`, or copy the files from the server. This closes the direct download only; the console host remains the fix for the rest of residual risk 16 ([threat model](../threat-model.md#backup-download-part-of-2225), residual risk 16). A single-organization install with it unset can download.
  - **Several nodes.** A link answered by a node whose backup directory isn't the click node's is `409` `other_server`, and a row whose files are in another server's directory says so instead of offering them. Route `/editor/backups*` to one node, or share `BACKUP_DIR`. For an imported or older row on nodes without a `.kiln-dir-id`, the `409` can't fire.
  - **Upgrade.** No migration and no setting; rolling the pin back is safe (an older release lists `backup_downloaded` events as "Unrecognized event (backup_downloaded)"). During a rolling deploy a download request that reaches an older node answers `404`: click again. Why it works this way: [ADR 0089](../decisions/0089-a-platform-admin-downloads-a-local-backup-file-through-a-one-minute-link-and-never-while-the-console-shares-an-origin.md).

<a id="sign-out-everyone-every-site"></a>

- **A platform admin can sign out every session on every site in one step (#2491).** A site's **Sign out everyone** (#2246) reaches only that site, and leaves headless app tokens alone, so ending every session on the server meant visiting each site, and app tokens needed a password reset or **Sign out everywhere**, one account at a time. **Sessions** (`/editor/sessions`) now has a section, **Sign out everyone on every site**, shown to platform admins only (a live temporary grant counts). The guide is [Sign everyone out on every site](../account-administration.md#sign-everyone-out-on-every-site).
  - **Confirming.** Type the server's host name (`PHX_HOST`, as the field's label shows it; any case, spaces around it ignored, not translated) and click **Sign out everyone on every site**; the button stays disabled until it matches, and the action compares it again. **Keep this session signed in**, ticked by default, keeps only this browser on this host and its remember-me cookie. You see "Signed out 240 sessions on every site." Two installations with the same `PHX_HOST` value, such as two left unset, share the phrase.
  - **What ends.** Every unexpired browser session, remember-me cookie, sign-in waiting at the two-factor prompt and headless app token (`POST /api/auth/sign_in`) of every account, bound to a site or not, in one transaction. Open pages go to sign-in with "An administrator signed everyone out. Sign in again to continue.", and collaborative-editing rooms and `/ws/gql` sockets opened with those sessions close. API keys and password-reset, confirmation and magic-link tokens are untouched. The count is sessions and app tokens.
  - **Who and how it is recorded.** `KilnCMS.Accounts.InstanceSessions` `:sign_out_everyone`, platform admins only by policy; site admins, API-key actors and system actors are refused. From code: `KilnCMS.Accounts.sign_out_everyone_on_every_site(%{confirmation: phrase, except_session_jti: jti}, actor: admin)`, returning `{:ok, count}`. The instance security log records `all_sessions_revoked_everywhere`, "Everyone signed out on every site", with `count` and `except_self`; if that cannot be written nothing is signed out. No site's own log records it and no security alert is raised.
  - **Bounded.** The rows are locked in jti order before they are rewritten, so a session being used at that moment makes the sign-out wait instead of deadlocking it, and each statement may run for two minutes. Past that nothing is signed out and the page says "Nobody was signed out: it took too long and was undone. Try again." The site's own **Sign out everyone** now works the same way, with the same two-minute bound. A session signed in during the moment between the lock and the rewrite is signed out too but not counted, and its open pages close on their next request.
  - **No migration; rolling the pin back is safe.** An older release sends a person signed out this way to sign-in with no message, and lists the event as "Unrecognized event (all_sessions_revoked_everywhere)".

<a id="scanner-guard-refusals-no-alert"></a>

- **A request refused by a temporary rule the scanner guard added no longer raises the `blocked_ip` alert (#2810).** The guard already records `ip_auto_blocked` when it adds the rule, and the refusals that follow are the rule doing its job, not news for the site's admins; an alert every 15 minutes about them buried the alerts about rules an admin chose. See [Blocked addresses raise one alert per window](../security-alerts.md#blocked-addresses-raise-one-alert-per-window).
  - **What still happens.** The refusals are still written to the security log as `ip_block_refused`, sampled the same way, with one more metadata key, `source` `scanner_guard`, on those events only. They raise no alert and are left out of the window's summary, so a `security.blocked_ip` webhook endpoint gets fewer deliveries on a site where the scanner guard is on (`KILN_SCANNER_BLOCKING`). A refusal by an admin's rule alerts as before, and its event and webhook payload are byte for byte what they were.
  - **Who added a rule.** `KilnCMS.CMS.IpBlockRule` gains `source`, `admin` or `scanner_guard`, set from the actor that created the rule (`KilnCMS.CMS.Changes.SetIpBlockSource`) and never from input, so a person cannot make a rule of their own silent. A rule is not on any API, so nothing changes there. Where an admin's rule and an automatic one both contain the address, the admin's rule is the one matched, and it alerts. As before, an admin cannot add a rule for exactly the range of an active automatic one ("That range is already blocked."); remove the automatic rule first.
  - **Separate caps.** The in-memory gates in front of the alert now count each source apart: 20 client networks per site per 15-minute window, on each node, for admins' rules and another 20 for the scanner guard's (before, 20 in all). A scanner flood can no longer use up the samples an admin's rule gets.
  - **Wording.** The setting on **Security alerts** is now **Requests from blocked addresses** (it was **Blocked addresses**, the name of the block list's own page), and its description reads "A request from an address on this site's block list is refused. Temporary rules the scanner guard adds don't raise it. One alert every 15 minutes, then a summary. On by default. Your block list is under Sign-in & access → Blocked addresses."
  - **For developers.** `KilnCMS.Security.IpBlocklist.match/2` returns `{:blocked, rule, source}`, and `KilnCMS.Security.BlockedIpAlert.note/5` replaces the four-argument `note`, taking the source before the surface; a source it does not know is treated as `:admin`, so it alerts. `KilnCMS.Security.Alerts.classify/2` raises nothing for an `ip_block_refused` with `"source" => "scanner_guard"`.
  - **Migration:** see the [upgrade note](#scanner-guard-rule-source-upgrade).

## Fixed

<a id="idle-component-activity"></a>

- **Clicks inside a component now keep a session awake under a site's idle timeout, and the sign-out buttons say they close open editing rooms (#3464, part of #2491).** A site's idle timeout (#2246) counted a page's own events as activity but not events a LiveComponent handles itself (`phx-target={@myself}`): the notification bell, the content editor's reference pickers and reference fields. A person working only inside one of those could be signed out while using the page.
  - **What changes.** Every Kiln LiveComponent's `handle_event/3` is wrapped (`KilnCMSWeb.IdleSession.ComponentActivity`, registered by `use KilnCMSWeb, :live_component`), so an event it handles counts as activity the way a page's own events do, throttled as before. Replies a hook sends on its own (`body_flushed`, `push_state`, `push_unsupported`) still don't count, and a component on a page without the idle timeout (a public or anonymous page) sends nothing.
  - **New hints.** `/editor/sessions`, under **Sign out everyone**: "Sessions from before this was available are signed out the next time they're used here. Collaborative-editing rooms open on the signed-out devices close too." **Your settings → Active sessions**, when another session is listed: "Signing other sessions out, one at a time or all at once, also closes the collaborative-editing rooms open on those devices." An account's page in `/editor/accounts`: "“Sign out everywhere” also closes the collaborative-editing rooms this account has open on any device." Spanish and French included.
  - **The "sign out everyone" watermark's horizon is derived.** A site's **Sign out everyone** catches sessions that record no site through a watermark, which was checked for a fixed 30 days. It is now the longest of the session token's lifetime, the remember-me token's and a two-factor hold's (`KilnCMS.Accounts.IdleTimeout.watermark_horizon_seconds/0`), still 30 days today, so raising a lifetime in the sign-in configuration widens it too.
  - **Still open.** A page that reconnects re-sends its open forms, and the first of those counts as activity, so an idle tab that reconnects after a deploy just before its deadline stays signed in ([#3474](https://github.com/The-Verscienta/kiln_cms/issues/3474)). Counting component events extends that to component forms. Why a session belongs to the site it signed in on, and why the site decides its timeout: [ADR 0090](../decisions/0090-a-browser-session-is-bound-to-the-site-it-signed-in-on-and-is-signed-out-on-another-sites-host.md).
  - **For developers.** A component must `use KilnCMSWeb, :live_component`, not `use Phoenix.LiveComponent` directly (a test fails on one that doesn't), and must mark its callbacks with `@impl`, since the wrapper carries `@impl Phoenix.LiveComponent`.
  - **No migration, no setting; rolling the pin back is safe.** An older release goes back to ignoring component events and drops the hints.

<a id="field-schema-deadline"></a>

- **A slow schema build no longer refuses a valid JSON field value (#3063).** A `:json` custom field with a JSON Schema checks each written value in its own process under a 1-second deadline, so a pathological `pattern` fails the save with a message instead of holding the request. The schema was built inside that deadline too. The first build on a node loads the JSV builder, every draft 2020-12 vocabulary and the embedded meta-schema (about 20 modules, tens of milliseconds when idle, where a later build takes well under a millisecond), and on a busy node that could pass the second. The save was then refused with "took too long to check against the schema" although the value was valid.
  - **What changes.** The schema is built first, in the saving process, the same build that already runs unbounded when the field definition is saved. The deadline starts after it and covers only the check of the value.
  - **Unchanged.** The schema limits (16 KB, 16 levels, 1,000 values, no remote references), the value limits, the deadline and its message. A value whose check runs past the deadline is still refused. No migration; rolling the pin back is safe.

<a id="host-key-alert-per-destination"></a>

- **A changed SFTP host key raises an alert for each destination, even when two change in the same alert window (#3201).** The platform alert `backup_host_key_changed` claimed the one alert window that all platform alerts of a kind share. When a second server's key changed within the same 15 minutes, its `backup_destination_host_key_mismatch` event was written to the instance security log, but the window was already taken, so no alert named that destination.
  - **What changes.** The window is claimed per destination (scope `backup_destination:<id>`), so each destination's key change raises its own alert naming it. The event's own limit, at most one per destination per hour across nodes, still bounds how many one destination can raise. The alert can't be turned off, as before.
  - **No migration; rolling the pin back is safe.** An older release shares one window again.

<a id="publish-shows-unpublish-date"></a>

- **Publishing a draft without opening the editor shows its scheduled unpublish date (#2892).** This was a 1.13.0 known issue. A draft can carry a takedown date, **Scheduled unpublish at** in the editor (`unpublish_at`, with `expiry_action` saying what happens then), and [ADR 0051](../decisions/0051-taking-content-down-needs-the-same-approval-as-putting-it-up.md) leaves it ungated on a draft because whoever publishes the draft approves the date with the page. Only the editor showed it. An admin who approved a draft from the content list, the bulk bar or a release never saw the date, and the page came down at it.
  - **The content list.** A draft or in-review row with a date shows it beside its **Publish** or **Approve** button, as published rows already did: **Unpublishes**, **Archives** or **Flagged expired**, by the record's expiry action, then the time.
  - **The bulk bar.** The **Publish** confirm says how many of the selected drafts have a date ("2 of these have a scheduled unpublish date") and lists them soonest first, up to ten. Selected rows off the current page or filter are counted too.
  - **Releases.** Each pending publish item for a draft with a date shows it under the title, and the panel with **Schedule** and **Publish now** totals them.
  - **Unchanged.** Publishing works as before; nothing is asked or refused that wasn't. No migration; rolling the pin back is safe.

<a id="markdown-inline-image"></a>

- **An image that is not alone on its line of Markdown is kept (#2771).** This was a 1.13.0 known issue. `KilnCMS.Markdown.to_blocks/2` and `parse_document/2` rendered every image as `<img>` and left it to the HTML adapter, which lifts an image into an image block only when it is the whole of a top-level paragraph. Anywhere else, mid-sentence (`Our logo ![Acme](https://x.test/a.png) is blue`), two to a line, or in a list item, quote or table cell, the adapter had no inline node for it and dropped the picture and its alt text with no error. The stored text read "Our logo is blue".
  - **What changes.** Such an image stays where it was, as a link to the picture labelled with its alt text (or with its URL when it has no alt text). That is what pasting Markdown into a rich-text block already did. An image inside a link (`[![CI](badge.svg)](https://ci.example)`) becomes the link's text, and the outer link stays.
  - **Where.** Every path through the converter: the editor's Markdown view and `.md` import, `body_markdown` writes over JSON:API, GraphQL and MCP, and anything else that calls `KilnCMS.Markdown`.
  - **Unchanged.** An image alone in its paragraph, linked or not, still becomes an `image` block with its alt text and title as caption. Content stored before the fix is not repaired: the dropped image was never saved, so import that Markdown again.
  - **No migration; rolling the pin back is safe.** An older release drops such images again on the next Markdown write.

<a id="duplicate-rich-text-body"></a>

- **A duplicated text block keeps its text when it is saved (#2778).** This was a known issue in 1.13.0. A rich-text block's prose is held by the editor's server session, keyed by the block's id, and added back into the form on every keystroke, save and autosave; the form itself carries only an empty HTML field for it. Duplicating a block gave the copy a new id but never registered its prose under that id, so the first keystroke anywhere in the form, or the save itself, stored the copy empty while its editor still showed the text.
  - **What happens now.** The copy's prose is registered under its own id the moment it is made, taken from what the original holds at that point, typed but unsaved text included. Save, autosave and *Publish changes* store it, and editing the original afterwards leaves the copy's text alone.
  - **Other copy paths checked.** Duplicating a columns block already copied its nested blocks' text, which lives in the columns block's own state, and keeps doing so. Duplicating a whole document copies the saved record on the server and never read the editor's state. Copy and paste between blocks goes through the editor's normal typing path.
  - **No migration; rolling the pin back is safe.** A copy saved empty on an earlier release stays empty; its original, or a version in the document's history, still holds the text to copy back.

<a id="slack-missing-site-name"></a>

- **A Slack webhook message whose payload names no site names the endpoint's site (#2797).** `KilnCMS.Webhooks.SlackFormat` renders a Slack-format endpoint's body at send time from the ledger row's payload, and read the site from its `site_name`. A test ping queued by a 1.9 node while a rolling deploy to 1.10 was under way carries Kiln's ping payload (`message`, `endpoint_url`, `sent_at`) and no `site_name`, so the new node posted "KilnCMS webhook test for `-`". A security alert row without the key would have read "Security alert on `-`".
  - **What changes.** `KilnCMS.Webhooks.DeliveryWorker` fills in a missing or empty `site_name` from the endpoint's site (`KilnCMS.Branding.for_org/1`) before rendering a Slack body. If the renderer is still handed a ping without one, it says "KilnCMS webhook test" with no placeholder.
  - **Unchanged.** The job arguments are the same shape they were in 1.9, so no compatibility clause was needed; only the payload differed. The ledger row keeps the payload as it was queued, and Kiln-format endpoints are sent exactly what they were before.
  - **No migration; rolling the pin back is safe.** An older release renders such a row with `-` again.

Deleting a rule closed whatever edit form was open, another rule's half-typed changes included; it now closes only that rule's. <a id="reserved-route-slugs"></a>

- **A slug that a built-in route already answers is refused (#2898).** This was a 1.13.0 known issue. `KilnCMS.CMS.ContentTypes.reserved_path_segments/0` is the list the slug, path-alias and content-type validations check, and it had fallen behind the router: `GET /developers`, `/ready`, `/setup`, `/sign-in`, `/sign-out`, `/actor`, `/ap/...`, `/mcp` and `/password-reset/:token` are all declared ahead of the `/:slug` catch-all. A page slugged `developers` saved without error, and `/developers` kept serving the developer page.
  - **What changes.** Those segments are reserved. A page slug, a path alias's first segment, or a dynamic content type's path segment equal to one is refused with the existing reserved-slug error. A title-derived or regenerated slug steps around them (`developers-2`). Installed plugins' public and plug routes are declared ahead of `/:slug` too, so their first segments are reserved as well.
  - **Kept in step.** `KilnCMSWeb.ReservedRouteSegmentsTest` reads the compiled route table and fails when a GET route ahead of `/:slug` has an unreserved first segment. Names with a dot (`sitemap.xml`, `llms.txt`) are skipped: no slug or alias can contain one. `forms` and `newsletter` stay free, because every route under them is three segments deep and answers neither `/forms` nor `/forms/<slug>`.
  - **Unchanged.** Post and entry slugs live under `/blog/` or their type's segment, which no such route reaches, so `developers` is still a valid post slug. A dynamic type that already used a newly reserved segment can still be edited: its segment is checked only when it changes.
  - **No migration; rolling the pin back is safe.** Existing records are not changed; see the upgrade note for listing them.

<a id="fallback-mode-refire"></a>

- **Changing a custom field's localization to or from `:fallback` re-fires the type's locale variants (#2905).** A `:fallback` field that a variant leaves empty is filled from the next locale along the site's chain when the variant is fired, and the fired `:json` body names it under `inherited_fields`. Saving the chain at `/editor/locales` and publishing a variant re-fired the documents that inherit; changing the field's mode on the Fields screen re-fired nothing. A French page whose tagline was empty kept serving it empty, with no `inherited_fields`, after the field became `:fallback`, and kept serving the English tagline after it stopped being one, until that page was next published.
  - **What changes.** `KilnCMS.CMS.Changes.BustTypeRegistry` now re-fires the field's type when its `localization` changes to or from `:fallback`, and when a `:fallback` field is deleted. Only the type's published rows outside the default locale are queued (`KilnCMS.Firing.Sweep.sweep_type/3` with `only: :translations`): the default locale ends every chain, so it never inherits. A site with no translations queues nothing.
  - **Unchanged.** A switch between `:localized` and `:shared` re-fires nothing; a shared value is copied into the variants when the source publishes, as before. Creating a field as `:fallback` re-fires nothing either: no document holds a value for it yet.
  - **No migration; rolling the pin back is safe.** An artifact fired with the old answer on an earlier release is corrected by `mix kiln.refire_all`, or by publishing the variant.

<a id="plugin-typed-filters"></a>

- **A filter operand on a plugin field type with a typed GraphQL kind compares as a value of that kind (#2855).** A `custom_filter`, `customWhere` or MCP `custom_filter` operand on a plugin `Kiln.FieldType` was always compared as the text sent, against the stored jsonb. A type whose `graphql_kind/1` is `:int` stores a JSON number, and a jsonb string sorts below every number, so `eq` and `in` (`"42"` is not jsonb `42`) never matched, `gt` and `gte` matched every stored number and `lt` and `lte` none.
  - **What changes.** On a type whose kind is `:int`, `:float`, `:boolean` or `:date`, an operand that is a value of that kind compares as that value, as on KilnCMS's own field of the kind: `custom_filter[score][gt]=9` finds a stored `10`, `custom_filter[score]=42` a stored `42`, and a `customWhere` `int`, `float`, `boolean` or `date` condition on such a field matches what it names (a `date` one used to be refused).
  - **Unchanged.** Everything else compares as the text sent, as before, so no read that answered `200` is refused now: an operand that is not a value of the kind (`gt=ten`), `contains`, `starts_with` and `ilike` (`starts_with=1` still finds `10`), and every operand on a type whose kind is `:string`, `:datetime` or `:json` or that has no `graphql_kind/1` (a plugin's date-time spelling is its own). `custom_sort` already compared the stored jsonb. The console's list filters don't offer plugin fields, as before. See [extending-content.md](../extending-content.md#filters-on-a-plugin-field-type).
  - **No migration; rolling the pin back is safe.** An older release compares such operands as text again.

<a id="counted-read-refusal"></a>

- **A refused count-paginated read returns `Forbidden` (#2934).** A read with `authorize_with: :error` and `page: [count: true]` raised `Ash.Error.Framework` ("Invalid value returned from AshPostgres.DataLayer.run_aggregate_query/3") for an actor the policy refused, where the same read without a count returned `{:error, %Ash.Error.Forbidden{}}`. With `:error`, Ash turns the refusal into a filter that raises inside Postgres; AshPostgres hands that back as `{:error, :no_rollback, error}`, which Ash accepts from the rows query but not from the count query (seen on ash 3.38.1 and ash_postgres 2.15.2).
  - **What changes.** `KilnCMS.CountedRead.read/1` runs such a read with its count and, when the count fails that way, runs it again without one and returns that read's error: the refusal. The backup history's "Last scheduled run" lookup (`Backups.history_page_of/3`) counts through it. A canary test fails once Ash accepts the AshPostgres return, so the workaround can be removed then.
  - **Unchanged.** The JSON:API `page[count]`, GraphQL and MCP reads, and the console lists, authorize with Ash's default `:filter`: refused rows are left out of the page and the count, and the answer is never a 500. No migration; rolling the pin back is safe.

<a id="custom-where-error-spelling"></a>

- **A refused `custom_where` names its keys the way the caller's surface spells them (#2913).** `KilnCMS.CMS.Preparations.CustomFieldQuery` built every `custom_where` refusal in GraphQL's camelCase: "needs exactly one of string, int, float, boolean, date, dateTime", "customWhere supports only eq, notEq, in and isNull on it", "which customWhere does not support; use customFilter". The MCP read tools, JSON:API's query string and the code interface take snake_case, so a client or model that followed the message failed again (`unknown key "dateTime"`, `unknown operator "notEq"`).
  - **What changes.** Over MCP, JSON:API and the code interface the text names `custom_where`, `custom_filter`, `date_time`, `not_eq` and `is_null`, and reads "an int field" and "an int condition" where it read "a int". `docs/mcp.md` no longer warns that some messages use GraphQL's spelling.
  - **Unchanged.** GraphQL's messages are the same, word for word, so a client matching on them keeps working: the GraphQL schema marks a GraphQL request in the Ash context, and only then are the keys spelled in camelCase. The conditions each surface accepts are the same as before.
  - **No migration; rolling the pin back is safe.** An older release spells these messages the GraphQL way again.

<a id="gen-plugin-overlay-config"></a>

- **`mix kiln.gen.plugin` writes an overlay plugin's registration into the overlay (#2910).** The generator registered the plugin with `config :kiln_cms, :plugins` in `config/config.exs`, the core's tracked config, so a downstream overlay's plugin landed in the reusable core. The overlay's activation file is `projects/<name>/project.exs`, which dev copies to the git-ignored `config/project.exs` and the image build copies with `--build-arg PROJECT=<name>`, and its `:plugins` list replaces the core's rather than adding to it.
  - **What changes.** The generator creates `projects/<name>/project.exs` with the plugin in its `:plugins` list, or adds the plugin to that list if the file already exists, and leaves `config/config.exs` alone. The plugin and its sample block or field type go live once the overlay is activated; the notice now opens with that step.
  - **The notice.** It also lists the per-type search-vector migration a hand-written content type needs: `mix ash.codegen` cannot create the trigger-maintained `search_vector` column, so the type needs a migration calling `KilnCMS.Migrations.add_search_vector/1`, sorted after the one that creates its table. `mix kiln.search.check` fails without it.
  - **`@impl`.** Checked: the generated plugin compiles under `--warnings-as-errors`, including every commented example once uncommented, because an overridden `Kiln.Plugin` callback inherits `@impl` from `use Kiln.Plugin`. The one example that warned was the field type's `handle_input_event/3`, which has no default to inherit from and bound an unused variable; it now has its own `@impl Kiln.FieldType`.
  - **Unchanged.** `--dep` plugins still touch nothing in the checkout. A plugin generated by an earlier release keeps its `config/config.exs` line until you move it into the overlay's `project.exs`. No migration.

<a id="plugin-widgets-full-definition"></a>

- **The fields admin asks a plugin field type for its editor inputs with the whole definition, as the save does (#2883).** A `Kiln.FieldType` that offers a choice of editor input lists it from `widgets/1`, which is handed the field's definition. The save asked with the whole definition the write would store. The **Editor input** cards on `/editor/fields` asked with a definition built from six posted settings (type, `multiple`, new terms, text format, options and the number bounds) laid over the stored field. A type whose list reads any other setting, such as `required`, `name` or another constraint, got a different answer on the page: the admin could pick a card the save then refused, or never see one the save would take.
  - **What changes.** The cards are asked with the form's own changeset, applied the way the save applies it, so the page and the save hand `widgets/1` the same definition. A card checked before a setting change that stops offering it is still dropped back to the default rather than refused; the page now decides that from the validated form instead of from the six settings. `mix kiln.plugins.doctor` asks `widgets/1` with one full sample definition in both of its checks.
  - **For plugin authors.** The `widgets/1` doc in `kiln_plugin` now says what the definition holds. Core field types are unaffected: their inputs read only the settings the page already sent.
  - **No migration; rolling the pin back is safe.**

<a id="feed-relay-exit"></a>

- **A change-feed event reaches this node's subscribers when the database connection exits mid-publish (#2938).** Before handing an event to the site's relay, `KilnCMS.Delivery.Feed.publish/4` decides what anonymous SSE streams see, which reads the event's exposure. The read failing with an error already hid the event from streams and delivered it anyway. Failing with an *exit* did not: a connection that went away while the read waited for it (a pool restarting, an owner process dying) skipped the hand-off, so live editor views and other in-BEAM subscribers on that node never got the event, and the log said "Feed event for … not published".
  - **What changes.** Any failure of that decision, a raise or an exit, now hides the event from SSE streams and still hands it to the relay. It logs `Feed event <id> hidden from streams: <reason>`.
  - **Unchanged.** Streams fail closed as before: an event whose exposure cannot be read or written is never shown to an anonymous subscriber. Delivery is still at most once.
  - **No migration; rolling the pin back is safe.** An older release drops such an event for local subscribers again.

<a id="reevaluate-interrupted-import"></a>

- **An imported backup recorded as Interrupted is rewritten once its stamp turns out complete (#2846).** The importer records a cron stamp with a `.partial` beside it, untouched for 3 hours, as **Failed** with "Interrupted: the backup stopped before it finished and left .partial files behind" (#2478). An older `backup.sh` with no heartbeat, or clocks that disagree badly, could get a run that was still going recorded that way, and the row said Failed for good, although the backup finished.
  - **What changes.** Every import now looks again at its own Interrupted rows. When the stamp has no `.partial` left, every file is still there and settled (10 minutes), and every kind the row names is complete (a covering `manifest.json` that succeeded, or a full set with its checksum sidecar), the row is rewritten once with what importing the stamp now would record, usually **Succeeded**. Its log gains "Re-evaluated: the stamp's .partial files are gone and its set is complete"; its start time, trigger, `keep_days` and earlier log lines are kept. A cron `all` killed during media stays Interrupted: it is never turned into "Succeeded, database only". See [If the run finished after all](../backups.md#if-the-run-finished-after-all).
  - **Refused, and not counted as a failure:** a row that retention has marked `pruned` anywhere, or one another node already rewrote. The write locks the row and checks it as locked.
  - **Retention's `pruned` mark locks the row too.** `Run`'s `:mark_pruned` now takes `names`, `key` and `at` and computes the marks from the locked row, so a mark can't be lost to a re-evaluation that read the row first. `KilnCMS.Backups.Recorder.mark_pruned/2` is unchanged.
  - **For operators.** `KilnCMS.Backups.Importer.run/0` and `retry_failed/0` return a `reevaluated` count beside the others; a rewrite whose write fails counts under `failed` and shares the import backoff. The two new `Backups.Run` actions (`:interrupted_imports`, `:reevaluate_interrupted`) are the `:backups` system actor's alone ([policy matrix](../policy-matrix.md)). [ADR 0033](../decisions/0033-backup-history-is-rows-only-the-backup-pipeline-writes-and-the-files-stay-the-truth.md) is amended with the exception and its one accepted gap.
  - **No migration, no setting; rolling the pin back is safe.** During a rolling deploy a node still on the older release marks `pruned` without the lock and re-evaluates nothing, as before. A row rewritten before a rollback stays rewritten.

<a id="send-time-suppression-forms-automation"></a>

- **Form mail and automation email check the suppression lists when they send (#3051).** A relay that hard-bounces an address puts it on the instance-wide list (`/editor/mail`) or, for a site on its own relay, on that site's list (`/editor/site-mail`), so nothing is mailed to it again. Form notifications, form autoresponders, `send_email` rules and the four editorial-intelligence reactions never asked either list: they build their own mail and send it from the job, past the pipeline's queue-time check. A dead `notify_email` or a mistyped submitter's address kept being mailed on every submission, which is the pattern that gets a sending domain marked as spam.
  - **What changes.** `KilnCMS.Forms.NotificationWorker` (the form's `notify_email`), `KilnCMS.Forms.AutoresponderWorker` (the submitter's address) and `KilnCMS.Automation.RuleWorker` (a rule's `to`, for `send_email` and for intelligence findings delivered by email, the default) ask both lists when the job runs, in the job shapes of this release and of earlier ones. A listed address is sent nothing. The job **completes**: it is not canceled, so it is not listed among the delivery failures on `/editor/mail` or `/editor/site-mail`, and its private args (form data, a legacy autoresponder's `to`, an automation job's sealed document) are dropped as on any finish. Findings delivered as a comment or a task send no mail and are not checked.
  - **An unreadable list retries.** If either list cannot be read, the job raises and Oban retries it, keeping its args until the last attempt, rather than sending past a list nobody read. The stored error does not name the address. An intelligence reaction asks before it loads the document or calls a generator, so neither a skip nor a retry spends tokens; this is now the one failure those reactions retry ([automation.md](../automation.md)).
  - **For admins and operators.** A skip logs, without the address: a warning `form notification job <job_id> not sent: form <form_id>'s notify address is suppressed (org <org_id>); clear it on /editor/mail or /editor/site-mail`; at info level `form autoresponder job <job_id> not sent: the submitter's address is suppressed (form <form_id>, org <org_id>)`, since the visitor typed that address; and a warning ``Automation rule <rule_id> sent nothing: its `to` address is suppressed (org <org_id>); clear it on /editor/mail or /editor/site-mail``. When a form's or a rule's mail stops arriving, look for those lines and **Remove** the address under **Delivery health** on the page that lists it. See [forms.md](../forms.md) and [direct-email-delivery.md](../direct-email-delivery.md).
  - **For developers.** `KilnCMS.Mail.check_suppression/2` returns `:ok` or `{:skip, :suppressed}` for a `with` step, and raises when a list cannot be read, as `KilnCMS.Mail.suppressed?/2` does. The workflow and task mail workers use it too; their behavior is unchanged.
  - **Unchanged.** The delivery pipeline, bounce recording and the admin test send (still not suppressed). Mail queued through `KilnCMS.Mail.enqueue!/2` is still checked only when it is queued, not again when `KilnCMS.Mail.DeliveryWorker` sends it ([#3446](https://github.com/The-Verscienta/kiln_cms/issues/3446)).
  - **No migration; rolling the pin back is safe.** During a rolling deploy a node on the older release still sends these mails without checking either list. This also adds the last test for [#2992](https://github.com/The-Verscienta/kiln_cms/issues/2992): a finished autoresponder job's row holds only its ids.

<a id="mention-roster-scoping"></a>

- **An account with no site membership is mentionable on the default site only, and a mention roster that can't be read now says so (#3047, #3052).** The mention roster decides who the editor's `@` dropdown suggests, who an `@name` in a comment resolves to, and, when a queued mention mail is sent, whether its recipient is still entitled to it. It read an account with no membership row anywhere as belonging to every site. So on a multi-site install, someone removed from the only site they belonged to (removal deletes the row) could still be suggested, mentioned and mailed on every site, a gap v1.11.0 documented as a limitation.
  - **What changes.** On any site other than the default site, an account with no site membership anywhere is no longer suggested, resolved or mailed by a mention. It still counts on the default site, as for every other permission: the roster now follows the same rule as `KilnCMS.Accounts.Scoping.effective_tier/2`. A platform admin with no membership, including one holding a live temporary admin grant, stays mentionable on every site. Active members of the site are unaffected.
  - **Queued mentions.** A mention mail queued before someone left the roster is checked when it is sent and skipped. Someone who wrote the content or has a comment on its thread is still mailed, as the thread notice the mention replaced ([#3048](https://github.com/The-Verscienta/kiln_cms/issues/3048) covers that rule).
  - **A failed roster read is reported (#3052).** A mention that cannot read its candidates still fires for no one, and the comment is still saved. Before, nothing said so. Kiln now logs a warning, `mention roster could not be read; mentions on this site resolve to no one (<ExceptionModule>)`, naming the exception's module only, never its message or anyone in it. When the content editor can't read the roster as it opens, each block's comment box shows "Mention suggestions couldn't be loaded. Reload to try again; an @mention sent now may notify no one." Spanish and French included.
  - **For developers.** `KilnCMS.Notifications.fetch_mention_roster/1` returns `{:ok, users}` or `:error`, for a caller that shows the roster to someone. `mention_roster/1` still returns `[]` on a failed read, and `mention_roster_member?/2` still raises.
  - **No migration, no setting; rolling the pin back is safe.** An older release reads membership-less accounts as on every site's roster again.

<a id="erasure-drops-suppressions"></a>

- **Erasing an account takes its address off every mail suppression list (#3036).** A relay's hard bounce puts the address on a suppression list: the instance list for the operator's relay, a site's own list for that site's relay. Nothing removed those rows except an admin, so an erased person's address stayed readable on `/editor/mail` and `/editor/site-mail` indefinitely, after the rest of the account had been anonymized.
  - **What changes.** Erasure (the `:anonymize` action: a platform admin removing an account, a registration rejected with erasure, and the staging scrub's anonymization) deletes the rows for the address the account held from the instance list and from every site's list, matched case-insensitively. It runs in the erasure's own transaction, right after the mail step that strips the address from finished mail jobs (step 17 of erasure in [Data flows](../data-flows.md#subject-rights-workflows)). If any list's delete fails, the erasure raises and rolls back as a whole, so it can be run again. The log line names the list (the instance list or the org id) and the error's module, never the address.
  - **The cost.** A suppression row is a recorded bounce, not a "do not contact" request. Once the account is erased nothing of the account's can be mailed. If the address is mailed again by anything that checks the lists, a relay that still rejects it bounces it at most once more, and that bounce puts it back on that relay's list.
  - **Not reached.** Accounts erased before this release keep their rows: their address on the account is already a tombstone, so there is nothing to match them by, and there is no backfill. An admin removes such a row on `/editor/mail` (instance list) or on the site's `/editor/site-mail`. An erasure run on a node still on the previous release during a rolling deploy keeps the rows too.
  - **Staging scrub.** It still empties both lists. It anonymizes accounts before it purges, so its `suppressed_recipients_purged` and `site_suppressed_recipients_purged` counts no longer include the rows that matched an account's address.
  - **For developers.** Both `KilnCMS.Mail.SuppressedRecipient` and `KilnCMS.Mail.SiteSuppressedRecipient` gain a destroy action, `:forget_erased`, that takes the address as a required `email` argument and deletes only that address's rows. It is actor-less only: any request that carries an actor is refused, the platform admin, the site's admin and `KilnCMS.Mail.system/0` included ([policy matrix](../policy-matrix.md)). `KilnCMS.Mail.forget_suppressions/2` is the one caller. Reading, recording and clearing a row with `:destroy` are unchanged. Why drop the rows rather than keep or hash them: [ADR 0091](../decisions/0091-erasure-drops-the-erased-address-from-the-suppression-lists.md).
  - **No migration, no setting; rolling the pin back is safe.** An older release goes back to leaving the rows; the rows already deleted stay deleted.

<a id="cache-fill-after-bust"></a>

- **A lookup that read before a save can no longer put the old answer back in the IP block list or host cache (#2972).** Both caches fill in two steps, read then store, and a save busts them once it commits. When the commit and the bust both landed between a lookup's read and its store, the bust deleted nothing and the store came after it. An IP block rule added or removed (in the console, by the scanner guard, or with `KilnCMS.Release.remove_ip_blocks`) could then stay unenforced, or stay enforced, on that node for up to a minute. After a site's `slug` or `custom_domain` changed, the new host could be cached as unknown (a `404`) for up to a minute, and the old one keep resolving for up to five.
  - **What changes.** `KilnCMS.Cache.FillGuard` orders each store against each bust in the cache's own transaction queue. A bust records when it ran; a lookup that began before it answers its request with what it read and stores nothing, so the next request reads the saved data. This holds on every node from the moment the cluster bust message reaches it. See [ip-blocking.md](../ip-blocking.md#how-fast-a-change-takes-effect) and [multi-tenancy.md](../multi-tenancy.md#change-the-slug-or-custom-domain).
  - **New metrics.** `kiln_cms.cache.fill_discarded.count` counts lookups served but not stored (`reason`: `busted`, or `too_old` for one that ran over five minutes). `kiln_cms.cache.bust_unmarked.count` counts busts that deleted but could not record their mark (`reason`: `mark_failed` or `queue_unavailable`), each with a warning, `FillGuard: a bust of <cache> deleted but left no mark (<reason>)`; a lookup already in flight may then still store its old value until the TTL. Both are tagged `cache`. See [observability.md](../observability.md#cache-fills-discarded-after-a-bust).
  - **Unchanged.** The request that straddled the save is still answered from what it read, once. A node that misses the cluster message still waits out the TTL. The cluster bust message is the same, so a node on an earlier release still honors it during a rolling deploy. The settings and published-content cache (#3431), firing artifact bodies (#3433) and the media cache bust (#3432) are not guarded yet.
  - **No migration, no new configuration; rolling the pin back is safe.**

## Security

<a id="scanner-guard-ipv6-rotation"></a>

- **A spoofed search-engine claim can no longer dodge the smart 404 guard by rotating through its IPv6 `/64` (#2838).** With `KILN_SCANNER_BLOCKING` on, `KilnCMS.Security.ScannerGuard` counts an IPv6 client as its `/64`, but a claim to be Googlebot (or another search engine) is checked per address, and a claim whose lookup was still running or had not started kept the exemption from the miss threshold. A scanner sending each request from a fresh address in its `/64` was therefore always judged before its own lookup finished, and its misses were never counted.
  - **What changes.** When a lookup of a request's own address finishes with the claim proven false, or with its reverse (PTR) query unanswered while this node's resolver answers others, the node marks the address's `/64` for an hour. In a marked `/64`, a claim DNS has not proven either way (pending, skipped, DuckDuckBot over IPv6, which has no DNS check) counts like any other client; so does a PTR silence during a resolver outage, when another address in the `/64` was proven false. A lookup that verifies an address clears a mark left by an unanswered PTR query, never one left by a proven-false claim.
  - **Unchanged.** A verified claim is exempt in any `/64`, and bait paths count for everyone as before. A forward query left unanswered in the engine's own zone keeps the exemption, as [ADR 0054](../decisions/0054-in-crawler-verification-a-silence-the-claimant-controls-counts-against-it-and-one-the-vendor-controls-does-not.md) decided. IPv4 is counted per address and has no marks. A lookup turned away by a cap or a busy slot marks nothing, since an attacker can spend those from other networks. The rate limiter's charges are unchanged, and there is no new telemetry. A DuckDuckBot claim outside DuckDuckGo's fresh list is still proven false and counted (#2852 is not part of this change).
  - **Who notices.** Only sites with the 404 guard on: nothing is marked while it is off. A real crawler sharing a `/64` with a liar (a hosting provider's customers) has its unverified first requests counted there for the hour; its verified addresses stay exempt. Such a block expires, and an admin can remove it on `/editor/ip-blocks`.
  - **For operators.** Marks are per node, in memory: a bounded Cachex of its own (`:kiln_cms_crawler_verification_networks`, 10,000 networks), never a database write. Two new code-config keys on `config :kiln_cms, KilnCMS.CrawlerVerification`, with no environment variable: `:network_mark_ttl_ms` (1 hour, restarted by each new mark) and `:max_network_marks` (10,000). The residuals, such as the first lookup deadline of exempt misses on each node and a `/64` whose lookups are all refused, are in the [threat model](../threat-model.md#bot-budgets). [ADR 0086](../decisions/0086-an-ipv6-64-that-produced-claimant-controlled-negative-evidence-loses-the-404-exemption-for-unproven-claims.md) records the decision.
  - **No migration; rolling the pin back is safe.** An older release has no marks and goes back to exempting every unproven claim.

<a id="crawler-claim-evidence"></a>

- **The smart 404 guard no longer blocks a real DuckDuckBot for DuckDuckGo's list lag (#2852), and no longer lets a spoofer typing "DuckDuckBot" from an IPv6 `/64` skip the miss threshold for good (#3450).** Both apply only with `KILN_SCANNER_BLOCKING` on. DuckDuckBot is the one search engine with no reverse-DNS check, so its published list (IPv4 only) is the only evidence about its claims, and the guard read it wrong both ways.
  - **Outside the list, over IPv4: counted after a day's grace.** Since #2586 an address outside DuckDuckGo's fresh list proved the claim false and the guard counted it at once, so a real DuckDuckBot crawling from an address DuckDuckGo had just added could be blocked until the next fetch. Such a claim is now `{:unverified, :not_listed}`. The guard keeps its exemption until the address is still outside a list fetched at least 24 hours after the instance first saw it miss; a vendor publishes a new crawler address within a day, a spoofer's never appears. In a marked IPv6 `/64` (#2838) it counts at once, and bait paths count for everyone throughout.
  - **The first sighting is the instance's.** It is kept in the database, dated by the database's clock, so a deploy, a restart or another node does not start the day again. It lapses after 48 hours with no miss from the client, or when the hourly prune removes it, and the next miss starts a new grace.
  - **Over IPv6, a claim tally.** A DuckDuckBot claim over IPv6 can be checked against nothing, and until now kept the exemption in any `/64` no other claim had marked. Now the first `threshold` such misses from one `/64` in a window are exempt (a counter of their own, `scanner_404_claim`), and each one after that counts toward the miss threshold like any other miss. A `/64` sending only DuckDuckBot claims is blocked on miss 121 of a 10-minute window with the defaults (`2 × KILN_SCANNER_BLOCKING_THRESHOLD + 1`); one mixing them with ordinary misses is blocked once its ordinary misses plus its claims past the first `threshold` exceed `threshold`. This is how we read the owner's "count toward the miss threshold once their `/64` reaches N misses". The block's reason is `miss_threshold` and its `ip_auto_blocked` event is unchanged. There is no new setting.
  - **Unchanged.** The rate limiter still charges a DuckDuckBot claim outside the list as no user agent (60 a minute with the defaults), whatever the guard decides. A verified claim is exempt everywhere. Over IPv4 an unverifiable DuckDuckBot claim (no fresh list, or `KILN_CRAWLER_RANGES=false`) keeps the exemption, and so does a claim whose forward query went unanswered in the engine's zone (#3451 tracks that one).
  - **What is left.** An IPv4 spoofer outside the list gets about 24 to 30 hours of miss exemption per address, still at the no-user-agent rate. While the database cannot answer, list-only claims a node has no copy for stay exempt. The stored key is an unsalted SHA-256 of the address (or `/64`), as in `throttle_counters`: pseudonymous, not anonymous (#3501 tracks an HMAC). The table has no row cap. The full list is in the [threat model](../threat-model.md#bot-budgets); [ADR 0095](../decisions/0095-a-search-engine-claim-nothing-can-prove-counts-toward-the-404-guard-only-on-evidence-a-real-crawler-cannot-produce.md) records why.
  - **For operators.** New code-config keys on `config :kiln_cms, KilnCMS.CrawlerVerification`, with no environment variable: `:listing_grace_ms` (24 hours), `:listing_ttl_ms` (48 hours), `:listing_refresh_ms` (5 minutes, how long a node trusts its cached copy of a sighting) and `:listing_retry_ms` (30 seconds, how long a node waits to ask again after the database could not answer), plus `:max_listing_entries` (100,000 cached clients per node). When the database cannot answer, the node logs "Crawler sighting store unavailable (…)" at `:error`, at most once a minute, and emits `[:kiln_cms, :crawler_verification, :sighting_unavailable]` (metric `kiln_cms.crawler_verification.sighting_unavailable.count`, tagged `reason`).
  - **For developers.** `KilnCMS.CrawlerVerification.check/3` gains the reason `:not_listed`; `{:unverified, :failed}` now always means DNS proved the claim false. `KilnCMS.CrawlerVerification.listing_overdue?/3` answers whether a list has had its grace, and `KilnCMS.CrawlerVerification.Ranges.age_ms/2` is now public. `KilnCMS.Security.CrawlerSighting` has no readable action; `KilnCMS.Security.CrawlerSightingStore` writes it in raw SQL.
  - **Migration:** see the [upgrade note](#crawler-claim-evidence-upgrade).

<a id="session-bound-sockets"></a>

- **A socket opened from a sign-in now closes when that sign-in ends (#2490).** Since #2246 a site's idle timeout and **Sign out everyone**, like the **Sign out** buttons under **Active sessions** (#1823), end sessions one at a time, so the account's other sessions are untouched. They sent each session's open pages to sign-in, but two sockets were known to the server only by account and outlived the session: the collaborative editor's `/ws/collab` room, whose token named only the user and lived a day, and a `/ws/gql` socket, which looked at its bearer JWT only at connect. The Sessions page said a browser was signed out while its room kept writing and its GraphQL socket kept answering. The browser's own **Sign out** told no open connection at all.
  - **What closes them.** Signing out one session from **Your settings → Active sessions** (**Sign out**, or **Sign out of all other sessions**), the site's idle timeout, the site's **Sign out everyone** and the browser's own **Sign out** each close that session's collab rooms and a `/ws/gql` socket opened with its token, at once. The browser's own Sign out closes only the sockets: that browser's other open tabs find the session gone when they next load a page or reconnect. Per-account sign-outs (*Sign out everywhere*, a password change or reset, and the rest) close every socket of the account, as before.
  - **Collab connects check the session.** A connect is refused when the session its token names is idle, revoked, expired, bound to another site, older than the site's last **Sign out everyone**, another account's, a remember-me row or a sign-in still held at the two-factor prompt. The channel's 30-second re-check, and the check every 200th update, repeat it, so a sign-out whose broadcast never arrived (lost between nodes, sent by a node on an older release) still closes the room within the interval. The re-check can also expire a session that went idle while none of its pages was open: the site's security log records **Signed out after inactivity** with `surface: "collab"`, without an IP address or user agent. The cost is one primary-key read of the token row and a cached policy lookup per re-check. An editor page that cannot name its session mints no collab token and edits on its own.
  - **`/ws/gql`.** A socket opened with a JWT is bound to that token and closes when it is signed out. Every document sent on it reads the token's row first; once the token is revoked, expired or gone, the document is answered, with nothing else run, by `{"errors":[{"message":"The bearer token this connection was opened with is no longer valid. Reconnect with a valid token.","extensions":{"code":"unauthenticated"}}]}`. The socket applies no site rule to the token, as `/gql` applies none: a headless token from `POST /api/auth/sign_in` is bound to no site, and a site's idle timeout and **Sign out everyone** still do not reach it. See [Connecting with a token](../headless-graphql-api.md#connecting-with-a-token).
  - **What is left.** A collab token minted before the upgrade is accepted, per account, for this release only ([upgrade note](#session-bound-sockets-upgrade)). A `/ws/gql` socket that only holds subscriptions sends no documents, so after a sign-out it missed it keeps receiving pushes until it sends one or reconnects. A node on the previous release revokes sessions without the socket broadcast during a rolling deploy. A token row that cannot be read fails open on both sockets. The full list is in the [threat model](../threat-model.md#idle-timeout-and-sign-out-everyone-2246).
  - **For developers.** `KilnCMS.Accounts.SessionEviction.session_socket_topic/1` is the per-session socket topic, `evict_session/2` and `evict_sessions/2` broadcast on it, and `disconnect_sockets/2` closes a session's sockets only. `KilnCMSWeb.CollabSocket.token/3` (was `token/2`) takes the session's jti; `KilnCMSWeb.BearerAuth.verify_token/1` returns the user and the jti; `KilnCMS.Accounts.IdleTimeout.check_row/3` runs `check/3` on a row already read. A new socket opened from a sign-in should subscribe to the topic after its last refusal and check its row, as [ADR 0087](../decisions/0087-a-socket-opened-from-a-sign-in-lives-no-longer-than-that-sign-in.md) says.
  - **No migration, no setting; rolling the pin back is safe.** An older release goes back to closing these sockets only on per-account sign-outs.
