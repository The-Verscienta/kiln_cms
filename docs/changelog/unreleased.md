# KilnCMS Unreleased — full release notes

The long-form entries behind the Unreleased section of
[CHANGELOG.md](../../CHANGELOG.md), as they were written when each change
merged. `CHANGELOG.md` carries the one-line summary of each; this file
carries the reasoning.

## Upgrade notes

<a id="direct-upload-claim-upgrade"></a>

- **The direct-upload cleanup fix takes effect once every node runs this release (#2724).** A completion now claims its upload's cleanup job before it reads the staged object ([below](#direct-upload-cleanup-claim)). During a rolling deploy, a `POST /api/media/uploads/complete` that lands on an older node doesn't claim, so it can still lose its staged object to a cleanup that comes due mid-copy, or to a concurrent completion; the client sees the old failure (`415 unsupported_media_type`) and starts the upload again. Nothing to configure, and no migration: the claim lives in the existing `oban_jobs` row (`meta` and `scheduled_at`).
  - **A token with no cleanup job can't be completed.** Completion now requires the job, so a token an older release issued when its cleanup failed to queue (it logged `staging cleanup was not queued`) answers `422 not_uploaded`. Start that upload again; what it staged is left to the bucket's lifecycle rule on `direct-uploads/`, if you have one ([media-pipeline.md](../media-pipeline.md#direct-uploads)).
  - **Rolling back is safe.** An older release ignores the claim in `meta`: a job a completion was holding runs when its lease ends, at most five minutes later, and deletes the staged object as before.

<a id="links-backfill-multiple-upgrade"></a>

- **If you ran the reference-links backfill on 1.5.0 to 1.12.1, run it again after upgrading (#2742).** On those releases `mix kiln.links.backfill` (or `bin/kiln_cms eval 'KilnCMS.Release.backfill_reference_links()'`) deleted every edge of a list reference field and never wrote it back; on 1.12.1 it also deleted every reference edge inside a group row or flexible item. The record values were untouched; what went missing is the `content_links` rows that backlinks, reverse reference fields, `max_sources` and the `on_target_delete` rules read ([below](#links-backfill-multiple)). You ran it if you restored a pre-1.1 backup, wrote `custom_fields` with raw SQL, or followed `mix kiln.join.retire`'s advice for an unmirrored field. The upgrade's own data migration (`20261003000000_backfill_reference_links`) lost nothing, unless you rolled back past it and migrated again on one of those releases.
  - **Run it once, in a quiet period.** `mix kiln.links.backfill`, or on a release `bin/kiln_cms eval 'KilnCMS.Release.backfill_reference_links()'`. It prints `Reference links: N written, M realigned, K removed.` It restores every top-level edge, single or list, with its position and link values. A save that lands while it runs can have its edge's position or link values set back to what the run read, until that record's next changing save.
  - **Nested edges are not restored by it.** A reference inside a group row or flexible item gets its edge back when that record's custom fields next change; saving it unchanged does not. A backfill that writes them is [#3357](https://github.com/The-Verscienta/kiln_cms/issues/3357).
  - **What a rerun can't repair.** A record purged for good while the edges to it were missing skipped its referrers' `on_target_delete` rule: a `:restrict` field didn't block the purge, and a `:clear` field left the purged record in its referrers' values, where it now shows as a broken reference. Find those in the backlinks panel and edit the referrer. A target may also now have more sources than its field's `max_sources` allows, since the backfill does not check the cap. Existing connections stay; a new one to that target is refused until it is back under the cap.
  - **No migration; rolling the pin back is safe.** Running the backfill on an older release deletes the list and nested edges again.

<a id="rename-rewrites-working-copies-upgrade"></a>

- **Drafts saved before a field rename or delete on 1.0.0 to 1.12.1 still hold the old key (#2744).** This release rewrites a live record's draft when a custom field is renamed, deleted or reshaped ([below](#rename-rewrites-working-copies)). It can't repair what earlier releases left behind, because nothing recorded which renames happened.
  - **A stale draft still drops the value.** A draft saved before a rename on an affected release holds the value under the old key, so *Publish changes* after the upgrade still drops it (and may report a conflict on *Custom fields*). Ask editors with drafts of live records that predate a field rename to re-enter the value under the new field, or to discard the draft.
  - **Values already lost are in version history.** Each version saved before the rename stores the value under its old key. Open the record's history, compare that version with the current document, and copy the value into the renamed field by hand. Restoring the version does not bring it back: a restore checks against today's definitions and drops a key none declares (the restore dialog lists it under *These custom fields will be discarded*).
  - **Affected releases.** Top-level fields since 1.0.0; reshapes and link fields since 1.5.0; group sub-fields since 1.6.0; flexible items since 1.11.0; held lists since 1.12.0.
  - **No migration; rolling the pin back is safe.**

## Added

<a id="condition-text-ops"></a>

- **Conditional fields can match text (#3270).** A **Show when** or **Required when** test in `/editor/fields` now offers **contains**, **does not contain**, **starts with** and **ends with** when it reads a text, URL or choice field: "show **Download notes** when **File URL** ends with `.pdf`". In a rule these are the operators `contains`, `not_contains`, `starts_with` and `ends_with`, each with a non-blank string `value`.
  - **Matching ignores case and surrounding spaces.** Both sides are trimmed, as for `eq`, and lowercased. The editor's evaluator and the server agree on non-ASCII text too (a Greek word-final sigma folds to ς on both); one shared fixture holds them to it.
  - **Lists and non-text values.** On a multiple field a test holds when any item matches, so **does not contain** holds only when no item contains the text. An empty value contains nothing. A number, yes/no or date field cannot use these tests: the definition is refused, and so is retyping a field to a non-text type while a text test reads it.
  - **Additive.** No migration. An older release reading a rule with one of these operators treats it as a rule it cannot read: the field is shown and not required, and the definition cannot be saved until the rule is changed.

<a id="flexible-search-diff"></a>

- **A flexible field can be searchable, and its version history shows item by item what changed (#2282, PR 6 of the flexible content field).** In `/editor/fields` the **Searchable (search indexes this value as text)** box now appears for a flexible field (**Names the record** is still not offered, and `names_record` is still refused). Search then finds a record by the prose in its items, and a version compare or restore preview lists each added, removed, changed or moved item instead of two walls of JSON.
  - **What is indexed.** Each item's text, read through its item type's sub-fields, in item order. Never an item's `_id`, `_type` or `_settings`, and never a **Media** or **Reference** sub-field (that value is a snapshot of something indexed under its own record). A nested flexible field is read down to the depth cap; an item whose type was deleted contributes by the generic rule, which skips those keys. The generic text walk, which a custom extractor can call as `KilnCMS.CMS.SearchableFields.default_texts/1`, now also skips `_`-prefixed keys of a map that has both `_id` and `_type`; any other map keeps its keys as before.
  - **Existing records.** Flipping `searchable` re-fires the type's published documents, which recomputes their search text (`updated_at` is left alone); a draft catches up on its next save. Changing which sub-fields an item type has does not re-index on its own: run `mix kiln.refire_all` afterward.
  - **History.** `KilnCMS.CMS.VersionDiff` adds an `items` list (`id`, `type`, `status`, `moved?`, `old_index`, `new_index`, `old`, `new`, `changed_keys`) to a custom-field entry whose old or new value is a list of items with unique `_id`s and a `_type`; items are matched by `_id`, so an edit is a change and a reorder is a move. Any other entry has no `items` key. The history screens list the items that changed or moved, with the item type's label and the text before and after (new public function `KilnCMS.CMS.FieldDisplay.display_item/3`). Stored versions, the API and webhooks are unchanged.
  - **Upgrade.** No migration, no new setting; rolling the pin back is safe, except that a flexible definition saved as `searchable` would then be refused when next edited, until the flag is cleared. Walkthrough: [Search a flexible field and read its history](../extending-content.md#search-a-flexible-field-and-read-its-history).

<a id="deliver-llm"></a>

- **A custom field's text can go in the fired `:llm` and `:json_ld` artifacts: tick "Include in AI-readable outputs" on a text, group or flexible field (issue 2282).** Answer engines read those two artifacts, and neither carried any custom field except geolocation, so an FAQ built from a flexible field never reached them. This is the last pull request of the flexible-content plan. In `/editor/fields`, **Edit** a top-level text (`:string` or `:text`), `:group` or **Flexible content** field and tick **Include in AI-readable outputs** (admins only). The row shows an **AI-readable** badge.
  - **`:llm`.** After the blocks, one `## <field label>` section per ticked field: a text field as a paragraph, a group as one `**Label:** text` line per text sub-field, a flexible field as a `### <item type>` heading per item followed by the same lines.
  - **`:json_ld`.** The main node gains `hasPart`, a list of `WebPageElement`s with `name` and `text`: one per text or group field, one per top-level item of a flexible field (named by its item type, nested items' text joined into it). An Event-family type gets none, as it gets no `articleBody`. Kiln's own pages keep their existing inline JSON-LD; the elements live in the fired artifact (`/api/content/:type/:slug?surface=json_ld`).
  - **A ticked container sends all its text.** Every text sub-field of a group or flexible field is included, nested items too, except a sub-field marked **Setting**; those texts become public. There is no per-sub-field switch. Numbers, media, references and choices are not included. A private field cannot be ticked.
  - **Caps.** At most 50 `hasPart` elements, and 5,000 characters per element or `:llm` section, cut at a word boundary with `…`.
  - **Off by default, so nothing existing changes.** Artifacts are byte-for-byte what they were until a field is ticked, so the artifact `format_version` does not change. Ticking or unticking a field, deleting a ticked one, or changing a ticked field's label, order, or the label, order, **Setting** flag or type of a field beneath it, re-fires the type's published documents.
  - **Upgrade.** Run `mix ash.migrate`: it adds `field_definitions.deliver_llm` (`boolean`, `NOT NULL`, default `false`). Rolling the pin back is safe; an older release ignores the column.
  - **Schema sync: an older release refuses a file with the option on.** `deliver_llm` is written to the field-sync file only when `true`, so a site that ticks nothing exports the same file as before. An older release reads `"deliver_llm": true` as an unknown key and writes nothing; export from the older build or delete the key ([field-sync.md](../field-sync.md#ai-readable-outputs-deliver_llm)). The `field_definition` resource in the JSON:API (`docs/api/openapi.json`) gains the boolean `deliver_llm`.
  - **How to and why.** [Put custom field text in the AI-readable outputs](../extending-content.md#put-custom-field-text-in-the-ai-readable-outputs), [geo.md](../geo.md), and [ADR 0082](../decisions/0082-a-fields-text-reaches-the-llm-and-json-ld-artifacts-only-when-its-container-opts-in-with-deliver-llm.md).

<a id="address-country-formats"></a>

- **An address field's editor follows the selected country (#2995).** Pick the US and the parts read **State** and **ZIP code**; the UK has a **County**, a **Town or city** and a **Postal code**; Japan a **Prefecture**; Ireland an **Eircode**; India a **PIN code**. A part the country does not use (no postal code in the United Arab Emirates) is not offered unless the stored address already has one, so a save never drops it. On a `required` field the browser also refuses a form missing a part the country needs (the US: line 1, city, state, ZIP code; the UK: line 1, town, postcode).
  - **Guidance, not a validation rule.** The server, the API and imports are unchanged: a country alone, or any subset of parts, is still a valid address, so existing clients and stored values keep working.
  - **The dataset.** `priv/address/formats.json` is generated by `scripts/address_data/generate.py` from [commerceguys/addressing](https://github.com/commerceguys/addressing) at a recorded commit. That library is MIT licensed, and its data derives from Google's libaddressinput, licensed CC BY 4.0. Both allow redistribution with the notices kept; `priv/address/NOTICE.md` carries them. A country the dataset does not list gets the generic format (a line and a city).
  - No migration, no schema or API change; rolling back is safe.

<a id="address-admin-area-lists"></a>

- **An address field offers the country's states, provinces or prefectures as a select (#2996).** For the 62 countries with a known list (the US, Canada, Japan, Australia, Brazil, the UK's local authorities and more) the administrative area is a select and the address stores its **code**: `CA`, not `California`; `13` for Tokyo. Other countries keep a text box.
  - **Lenient on the server.** `ca` and `California` both store as `CA`, and text that matches nothing (`England`) is kept as typed rather than refused, so existing values, imports and API clients keep working. A stored value that is not in the list stays selectable in the editor, so saving never changes or drops it. An address saved before this is converted to the code the next time it is saved.
  - **Search.** A `searchable` field indexes the stored code, not the area's name.
  - **Data.** `priv/address/subdivisions.json`, from the same MIT-licensed commerceguys/addressing dataset as [the country formats](#address-country-formats) (derived from Google's CC BY 4.0 libaddressinput data); notices in `priv/address/NOTICE.md`.
  - No migration, no schema or API change; rolling back is safe (a stored code is just text to the older release).

## Changed

<a id="list-item-error-position"></a>

- **A list field's errors name an item one way, by its position as the list is stored, counting from 1 (#2683).** On a list custom field (a list of numbers, dates, links, …), a type error counted items from 1 (`item 2 must be a date (YYYY-MM-DD)`) while a value rule (`min`, `max`, a length, `pattern`, a color palette) named the item by its index from 0 inside the field's name (`Scores (scores[1]) must be at most 10`). One save could report the same item as 2 and as `[1]`.
  - **What a message says now.** Both kinds name the item as `Label (name) item N`: `Scores (scores) item 2 must be at most 10`. N is the item's position in the list as stored, counting from 1: one item per line, with blank items and dropped repeats left out. It is the same N whether the save, the editor's field error, the JSON:API `detail` or the GraphQL `message` shows it.
  - **Type errors can name a lower N.** A list that drops repeats (every core list type but numbers, and a plugin type whose `unique_items?/0` is `true`) used to count a repeat before the bad item; it no longer does. `["2026-03-01", "2026-03-01", "soon"]` on a date list now reports `item 2`, not `item 3`. This holds for `mix kiln.fields.convert` reports too, which coerce each item as a save would. What is stored is unchanged: the first occurrence of a repeat stays, as before.
  - **Groups and flexible fields still count from 0.** A group row's sub-field (`dosages[2].unit`) and a flexible field's block (`sections[2]._type`) keep their 0-based paths in the message.
  - **API clients.** Only the human-readable text changed, and error text is not among the surfaces `docs/api.md` lists as stable ("Versioning & stability"). JSON:API still answers `code` `invalid_attribute` with `source.pointer` `/data/attributes/custom_fields` and no `meta`; GraphQL still answers `code` `invalid_attribute` with `fields` `["custom_fields"]`. A client that parsed `name[i]` out of the text should read `item N` instead, and subtract 1 for an index.
  - **French and Spanish.** The value-rule message is translated (`élément 2`, `elemento 2`), but type errors are not yet translated, so one list can show both `item` and `élément` (or `elemento`). Translating type errors is [#3324](https://github.com/The-Verscienta/kiln_cms/issues/3324).
  - **No migration; rolling the pin back is safe.** An older release writes the old messages again.

## Fixed

<a id="fields-slug-unique"></a>

- **A Slug field offers the Unique checkbox in `/editor/fields`, and saving a field no longer drops a constraint the form didn't post (#2780).** The Fields console mapped a field's type to the constraints it takes through a hand-kept list that left out Slug. A Slug field therefore showed no **Unique** checkbox, although it can be unique since 1.9.0, and editing anything on a Slug field that was made unique through the API or field sync (`/editor/fields/sync`, `mix kiln.fields.import`) (its label, say) saved it with no constraints and dropped `unique`.
  - **What changes.** The console reads the type from the registered field types (core, built-in and plugin), so every type shows the constraint inputs it takes, Slug's **Unique** included. A save also keeps any stored constraint the type takes that the form didn't post at all, so a form that doesn't show one can't drop it. A constraint whose input is posted blank is still cleared, and changing a field's type still drops the constraints the new type doesn't take.
  - **Unchanged.** Which constraints each type takes and how they are checked; a field inside a group or relationship, or one holding several values, still can't be unique.
  - **No migration; rolling the pin back is safe.**

<a id="auto-save-forms-no-recovery"></a>

- **A reconnect no longer replays forms that save as they change (#2782).** After a reconnect (a deploy, a laptop waking), LiveView resubmits each form on the page with the values it last showed. The Sections rows in `/editor/fields` save on change, so a page left open would post its stale **Shown as** and **Starts** for every section and silently revert another admin's newer choice, at the cost of one write and reload per section.
  - **What changes.** The Sections rows and the other console forms that save on change are left out of that recovery: a field's settings in the form builder, the **Add a tag** select in the media drawer, the content list's **Columns** picker and a backup destination's other-directory **adopt** checkboxes. After a reconnect they show what the server holds.
  - **Unchanged.** Forms that only preview or validate as they change still recover what was typed in them.
  - **No migration; rolling the pin back is safe.**

<a id="experiment-goal-select"></a>

- **The goal select on `/editor/experiments` takes effect (#2779).** The new-experiment form posts every field on each change, and the page's change handler matched on the content type first, so a change of the **Counts as a conversion** select was never read. Picking **A funnel is completed** left the form showing the **Goal form** picker, so the experiment was created with a funnel goal and no funnel, and could not be started. The same happened to **A page is reached**, whose target fields never appeared.
  - **What changes.** One change reads both the content type and the goal, so the picked goal shows its own target field and the funnel, form or page picked there is saved with the experiment. The document list is reloaded only when the content type changes, not on every keystroke in **Name**.
  - **Unchanged.** How a funnel goal is measured: a visitor converts on reaching the funnel's last step, as before. Who may create experiments, and which goal fields are saved for each goal.
  - **No migration; rolling the pin back is safe.**

<a id="collab-join-fallback"></a>

- **With live collaboration on, a rich-text block whose collab connection can't join now mounts a single-user editor instead of no editor at all (#2772).** A block bound to the collaboration room waited for its channel join before mounting TipTap, and that wait ended only on a successful join or a lasting refusal. A collab socket that never connected (a tab left open past the token's 24-hour lifetime and reconnecting after a deploy, or a proxy that drops WebSockets) or a join that timed out left the block without an editor until a full reload.
  - **What happens now.** The block stops waiting when the join times out, when the collab socket reports an error, when the join is refused (collaboration turned off, a stale bundle, the room unavailable), or after 15 seconds at most, which also caps an "over budget" refusal that phoenix.js keeps retrying. It then mounts the same single-user editor used when collaboration is off, seeded from the stored text and saving through the usual autosave, and shows "Live collaboration is unavailable, so others won't see your edits until you save. Reload to try again." under the block.
  - **A join that succeeds later doesn't apply.** The fallback leaves the room, and the document stays single-user on that page until it is reloaded, including blocks added or remounted afterward. A late join therefore can't bind a second copy of the text or overwrite what was typed in the meantime. Before this fix, a lasting refusal mounted a collaborative editor seeded from the stored text, and phoenix.js's next successful retry merged the room's copy into it, which could show the text twice.
  - **That tab saves its own text.** With another editor on the document, a tab in the room leaves autosave to one elected editor and shows "Synced live", since the room holds everyone's prose. A tab that fell back tells the server, and from then on it autosaves its own edits like a session with collaboration off. It can still meet a conflict when a collaborating editor saves the same record, as two editors without collaboration can.
  - **A reconnecting socket uses the newest token.** The collab socket used to keep the token of the first block that opened it, so after a deploy it reconnected with a token that had expired, and every document opened from then on waited on that dead socket. It now reconnects with the token of the most recently mounted rich-text block.
  - **Upgrade.** No migration, no new setting; rolling the pin back is safe. Only sites with the collaborative-editing prototype on (`:collab_prototype`) are affected.

<a id="redirects-refused-path"></a>

- **The Redirects form shows a refused path as an error on its field instead of crashing the page (#2763).** `/editor/redirects` created a manual redirect with the bang `CMS.create_redirect!`, so anything the `Redirect` resource refused raised out of the handler: the page crashed, reconnected, and the typed form was gone. A From path longer than the URL limit was enough, as was a locale longer than the identifier limit sent by a client, or a submit from an admin whose site tier had been lowered since the page opened.
  - **What the form does now.** It is an AshPhoenix form on `Redirect.create`, so the resource's own refusals come back as form errors: a length error shows under **From path** or **Locale**. The page's own checks land on their fields the same way: a path without a leading `/`, the root path and the target's own URL under **From path**, and a target that doesn't exist under **Target slug**. These used to be flash messages. What was typed is kept, so it can be corrected and resubmitted.
  - **Refused writes.** A create the policy refuses shows "You don't have permission to add redirects." as a flash, since no field is at fault, and anything else without a field shows "Couldn't create that redirect.". The target lookup no longer raises either: a lookup that fails reads as a missing target.
  - **Unchanged.** Who may create, list and delete redirects, the upsert on path and locale, and clearing a matching 404 counter after a create. Deleting a redirect already reported a failure as a flash.
  - **No migration; rolling the pin back is safe.**

<a id="visual-editing-prose-only"></a>

- **The visual-editing preview read stega-encodes only prose (#2770).** `GET /api/visual-editing/:type/:slug` appended its invisible field address to every string on a block except a short list (`_type`, `_id`, `_key`, `layout`, `gap`, `url`, `slug`, `locale`). Every other key was encoded, including the URLs and identifiers a front end uses as they are: a video's `src`, `poster` and `captions_url`, a file's `download_url`, an embed's `resolved_url` and `thumbnail_url`, a claim's `source_url`, every `media_id`, a file's `filename` and `content_type`, a form block's `form_slug`. A front end rendering the annotated preview then requested URLs that 404 and looked up ids that matched nothing.
  - **What is encoded now.** The document title, and on a block only the fields its block type declares plain-text translatable (`Kiln.Block.Info.translatable/1`): heading text, image alt and caption, video and audio titles and captions, a quote's text and citation, a file's title and description, and so on. Rich-text spans are encoded as before; code blocks still aren't. A plugin block follows its own `translatable:` declarations, and a block whose type isn't registered is left as is.
  - **A value check on top.** A string that reads as a URL (`https://…`, `mailto:…`), a path (`/media/…`, `../x.png`), a UUID, JSON or an identifier-like token (`video/mp4`, `report.pdf`, `contact_form`) is never encoded, even in a prose field. That covers a plugin field holding a URL that forgot `translatable: false`, and custom fields, which have no schema at this point and previously skipped only JSON and `http(s)` URLs. A one-word prose value with an inner dot, like a heading reading `Node.js`, loses its click-to-edit address as a result.
  - **Fewer clickable values.** Fields that are not translatable lose their address too: an embed's cached provider `title` and `author_name`, a custom block's `content`. None of them can be edited from the bridge.
  - **No migration; rolling the pin back is safe.** The public fired artifact was never encoded and is unchanged.

<a id="console-small-defects"></a>

- **Smaller console fixes from the November bug sweep (#2764).**
  - **A row deleted behind the page.** **Edit** on `/editor/webhooks`, `/editor/types` and `/editor/social` read the row with a raising call, so editing one that another admin had just deleted or archived crashed the page. It now says "That webhook (content type, account) no longer exists." and refreshes the list. **Remove** on `/editor/site-mail`, `/editor/site-storage`, `/editor/site-ai` and `/editor/site-search` did the same with the row read when the page opened; a removal that fails (the row already gone, or the admin no longer one) now says "Couldn't remove these settings. The page now shows what is saved." and reloads.
  - **Counts.** The newsletter's "N confirmed" heading counted the 100 newest subscribers it lists; it now counts every confirmed subscriber on the site, read as the signed-in admin. The overview's "All quiet." showed under open block tasks and unresolved block discussions; it now shows only when none of the lines above it does.
  - **Release times.** Go-live, published and rolled-back times on `/editor/releases` are stored and shown in UTC, beside a schedule field that takes local time. They now read `2026-11-25 14:00 UTC`.
  - **Checks.** A social announcement's link, which comes back from the remote instance, goes through the same href rule as every other link, so a `javascript:` URL is not linked. A crafted `create_translation` event on `/editor/translations` can no longer create a variant in a locale the site does not run, or in the default locale. The slug **preview** on `/editor/slugs` re-checks that the user is still a site admin on each run, as **apply** already did: it lists every record's title, drafts included.
  - **Not changed.** The funnel builder's handling of an unknown content type was already fixed; a test now holds it.
  - **No migration; rolling the pin back is safe.**

<a id="translations-slug-window"></a>

- **The translations dashboard's window is on slugs, not records (#2761).** `/editor/translations` read the 200 most recently updated records of each content type and only then grouped them by slug, so a slug could land in the window with some of its variants cut off. A translation older than the cut showed as **+ missing**, and clicking it failed with "Couldn't create that translation." because the variant already existed. When the default-locale source was the variant cut, the row was represented by a translation and its export checkbox was disabled with "No en source to translate from".
  - **What the window is now.** Per content type, the 200 slugs most recently edited in any locale, in the order the table sorts its rows; a slug that exists only in a non-default locale takes a place like any other. Every variant of those slugs is then loaded, so each row shows all the locales it has and is represented by its default-locale source when there is one.
  - **Unchanged.** Both reads run as the signed-in editor on the current site, exactly as the single read did, and the XLIFF export still loads the ticked records by id.
  - **No migration; rolling the pin back is safe.**

<a id="structure-trashed-parent"></a>

- **The structure page shows documents whose parent is in the trash (#2760).** Trashing a document is a soft delete that leaves its children's `parent_id` pointing at it, and `/editor/structure/:type` does not load trashed documents. The tree was drawn from the top level down, so those children, and everything beneath them, were grouped under a parent that was never drawn: they could not be seen, reordered or outdented, yet a published one still counted toward "in no menu". A type whose remaining documents were all in that state showed an empty page.
  - **Where they appear.** A document whose parent is not on the page (in the trash, or one you cannot read) is drawn at the top level with a **Parent unavailable** badge. Its own children stay beneath it.
  - **What a move writes.** Outdenting it, or dragging it to a new place at the top level, sets its parent to none, so restoring the old parent from the trash no longer puts it back underneath. Swapping it with the document next to it only changes the order, because either of the two could have been the one dragged. Indenting it nests it under the document above it, as for any other. Outdenting one of its children moves that child to the top level, rather than trying the hidden parent, which the move would refuse.
  - **Not changed.** Opening the page writes nothing. A badged document keeps its link to the trashed parent until you drag or outdent that document itself; a drag that only shifts it updates its position, so restoring the parent from the trash puts it back underneath. Nesting a document under one whose parent is in the trash is still refused ("is not a page in this site"); outdent the badged document first.
  - **No migration; rolling the pin back is safe.**

<a id="newsletter-exhausted-counts-failed"></a>

- **Every newsletter recipient ends in the campaign's counts (#2755).** A delivery that kept failing transiently (a recipient domain's MX down for the whole ~16-hour retry window, a greylist that never lifts, a relay that never answers) was retried eight times and then dropped by Oban with no counter moved, so the campaign showed `sent_count + failed_count` below `total_recipients` for good. Now the last attempt is the recipient's outcome.
  - **What counts as failed.** On the eighth attempt, a transient delivery error, any other raise, an unreadable subscriber, an exit, or the attempt running past the mail pipeline's 60-second ceiling counts the recipient in `failed_count` once and ends the job as cancelled, with the reason (`gave up after 8 attempts: …`) in the job's errors and a warning in the log naming the campaign and subscriber ids. A campaign whose content has no fired `:web` artifact now counts each recipient failed too; it was cancelled uncounted.
  - **What does not.** Earlier attempts still retry without touching the counts, and a permanent reject, counted as before, is not counted again. A subscriber who unsubscribed, hard-bounced or was erased between the fan-out and their delivery is skipped and still not counted, so a campaign's counts can sit below its total by that many.
  - **Upgrade.** No migration, no new setting; rolling the pin back is safe. Campaigns already sent keep their old counts.

<a id="api-key-unknown-scope"></a>

- **An API key whose scope this release doesn't know loads, and authenticates as nothing (#2604).** A key's `access` scope was a plain atom column, so a key minted by a newer release with a scope this one lacks (met on an older node during a rolling deploy, or after a rollback) failed every read that touched it: the key's own lookup at sign-in, the whole list at `/editor/api-keys`, revoking it, revoking an erased account's keys (erasure, the erasure backfill) and revoking a squatter's keys on invitation takeover. `access` is now a `KilnCMS.Types.KnownAtom`, as `docs/releasing.md` ("New values in an atom column") asks of a column that will grow, so the key loads with its scope as `%UnknownAtom{}`, and all of those work again.
  - **Refused, never read-only.** A new scope may grant less than read, so such a key must not fall back to its owner's reads. `User.valid_api_keys` admits only the scopes this release knows (`KilnCMS.Accounts.ApiKey.Scope.known/0`), so the key is refused exactly as a revoked one: the same `401` on JSON:API, GraphQL, `/mcp`, `GET /api/feed`, `GET /api/graphql/schema.graphql` and `POST /api/keys/rotate`, and anonymous on the bridge socket. Nothing is logged on the refusal: the key is simply not found, and logging it would cost an extra read on the unauthenticated path. That filter is the only gate for now; the drafts-only read clamps match `:draft_write` exactly, and hardening them is [#3316](https://github.com/The-Verscienta/kiln_cms/issues/3316).
  - **Rotation reuse still counts.** A rotated-away key presented more than 120 seconds after its rotation still revokes its chain, whatever its scope reads as; a live unknown-scope key with no successor is refused and burns nothing.
  - **In the console.** `/editor/api-keys` lists the key as **Unrecognized scope (name)**, with the stored name, and status **Not accepted** (an expired one reads **Expired**, as does an erased owner's). The status's tooltip says a release that knows the scope accepts it again, so revoke it if that isn't wanted. **Revoke** works as for any key.
  - **Security posture.** `core.api_keys` counts such keys in a new fact, `unrecognized_scope_keys`, and is **Review** for them, never **Fix now**; they are also named in **Details** when the check fails for an administrator's read-write key. `valid_keys` now counts only the keys that sign in on this release. During a rollout that adds a scope, older nodes warn and newer ones pass, and the JSON endpoint caches each node's answer for up to 30 seconds. The posture JSON contract is additive, so the new fact is not a breaking change.
  - **No migration; rolling the pin back is safe.** The column stays text. Mint keys with a new scope only once every node runs the release that added it; see `docs/releasing.md`.

<a id="beta-round-seat-audited"></a>

- **A new beta-round seat records its role grant, and an admin seat raises the new-admin alert (#2641).** `mix kiln.beta.round` wrote each new seat's account straight to the database with its role already set, so the security log had no `role_granted` for it and an admin seat raised no platform `new_admin` alert. An operator round mints admins, and on a shared beta or staging instance they appeared with no trace in the log and no word to the platform admins. An address that already had an account was handled correctly; only new seats were missed.
  - **What a new seat records now.** The account is still created pre-confirmed with a generated password and no mail, but at the default `viewer` role; its tier is then set through `User` `:manage_access`, the same action an adopted account and the **Accounts** page go through. The default site's log gets one `role_granted` with `level` `platform`, no person, and `previous_role` `viewer`. That `viewer` is the account's starting role for an instant inside the same transaction, never a role anyone signed in with.
  - **Alerts.** Each admin seat (the facilitator of an authoring round, every tester of an operator round) raises the platform `new_admin` alert to the platform admins. An editor seat raises no alert, as a platform role raised short of admin never does.
  - **One transaction per seat.** Creating a seat's account and granting its tier commit together: if the grant fails, the task raises and leaves no account for that seat. Seats made earlier in the same run stay, and their passwords are not printed because the task stops before the handout; re-run with `--reset-passwords` to issue them, which re-issues every existing seat's password, so not once testers are signed in.
  - **Still not recorded.** The first admin made at `/setup`, accounts from `priv/repo/seeds.exs` and the staging admin a scrub creates write no role event; `docs/security-events.md` ("Not recorded, and why") says why for each.
  - **No migration; rolling the pin back is safe.** An older release creates seats the old way again.

<a id="mcp-live-records-draft-only"></a>

- **MCP edits to a published record wait for a person (docs/mcp.md, "Live records").** `docs/mcp.md` said MCP authoring was draft-only, but `update_page`, `update_post` and `update_entry` ran the ordinary `:update` action, which writes the live row and re-fires a published record. A read-write key on an editor account could therefore rewrite a live page's text, SEO fields or slug, and readers saw it at once, even on a site where only admins publish.
  - **Refused over MCP.** `:update` now carries `KilnCMS.CMS.Validations.McpDraftOnly`, which refuses a published record when the call came through `/mcp` (`KilnCMSWeb.Plugs.McpSurface` marks the request with `kiln_surface: :mcp` in the Ash context). The tool error names the working-copy tool to use. It applies to every key on `/mcp`, an admin's included: the rule is about the surface, not the role. Drafts, records in review and archived records are edited with `update_*` as before.
  - **New tools.** `save_page_working_copy`, `save_post_working_copy` and `save_entry_working_copy` run `:save_working_copy`, the action the editor uses for a live document. They take `title`, the body as `block_tree` or `body_markdown`, and `fields` for the other held settings. `:save_working_copy` gains those three public arguments for them (the working attributes are internal), and `KilnCMS.CMS.Changes.ApplyBlocksInput` takes a `target:` so the Markdown conversion lands in `working_blocks`. They refuse a record that is not published.
  - **Not changed.** JSON:API `PATCH`, GraphQL and in-context editing still edit a live record directly, as `docs/working-copy.md` ("Not in this change") describes. A content link on a published source still shows at once.
  - **No migration; rolling the pin back is safe.** An older release lets `update_*` edit live records again and does not serve the working-copy tools. A project that overrides `config :kiln_cms, :mcp_tools` must add the three new names; without them a model cannot edit a published record over `/mcp` at all.

<a id="import-media-per-asset-deadline"></a>

- **A large single-origin import keeps its media: each image download has its own deadline (#2720).** The importers fetch one host's images one after another, so no host sees more than one request at a time, and that whole host group shared one 120-second timeout. A WordPress export points almost entirely at one origin, so any import whose images took longer than two minutes in total (a few hundred images at a second each) hit it. The kill landed mid-run: images already stored stayed in the media library with no post pointing at them, every post kept hotlinking the old site, and the report showed a single `(host group)` failure in place of hundreds of URLs. `mix kiln.import.wordpress`, `mix kiln.import.ghost`, `mix kiln.import.content` and their `KilnCMS.Release` functions were all affected.
  - **What happens now.** Each image gets 60 seconds, wall clock, for its download: DNS, connect, waiting for a SafeFetch pool slot and the body. The 5-second connect timeout and the 30-second limit on a connection that goes silent still apply inside it; the 60 seconds catches a server that trickles bytes. An image past the deadline is reported `{:fetch_timeout, 60000}` under its own URL and its block keeps the source URL; every other image is stored and linked as usual. The deadline stops before anything is written, so a cut-off fetch leaves no temp file, stored file or media item behind. The media phase as a whole has no time limit.
  - **A host that stops answering is cut off.** After three timeouts in a row on one host, its remaining images are reported `:host_unresponsive` without a request, and the log gets one warning naming the host. Without this, a dead origin would cost a timeout (up to 60 seconds) for every image it holds. A timeout here is the deadline or a connect or receive timeout; any other answer, a `404` or a refused connection included, resets the count.
  - **The trade.** One 25 MB file (the download cap) had up to 120 seconds under the old shared timeout; it now has 60, which needs about 420 KB/s sustained. A large file on a slower origin is now listed as failed, to upload by hand.
  - **Other new reasons in the report.** `{:fetch_crashed, message}`, `{:exception, message}` and `{:exit, message}` when the fetch or the store raised or exited (that image is skipped, the run carries on), and `:too_many_outbound_requests` when the node had no capacity to start the fetch.
  - **Progress for WordPress and Ghost.** Only the envelope import printed progress before. All three now print `media: N/T` and `records: N/T` every 25 items and at the end, so a long media phase shows it is moving.
  - **Re-running does not refetch.** A re-run only fetches images for the posts it is about to create, so images listed as failed are not retried. Upload them to the media library and swap them into their posts. `docs/content-portability.md` ("Images that could not be fetched") lists each reason.
  - **For library callers.** `KilnCMS.Media.Ingest.store_url/2` takes a new `:fetch_timeout` option (milliseconds, default no bound), and `KilnCMS.Portability.Import.run/2` takes `:media_fetch_timeout` (default `60_000`; anything but a positive integer means the default). A `:fetch_timeout` that is not `nil` or a positive integer raises `ArgumentError`. There is no CLI flag for either.
  - **Not fixed here.** An envelope import still does not sideload body images that resolve through the envelope's media manifest; they keep hotlinking the source. That is [#3326](https://github.com/The-Verscienta/kiln_cms/issues/3326).
  - **No migration; rolling the pin back is safe.** An older release goes back to the shared 120-second timeout.

<a id="changelog-stray-lines"></a>

- **`mix kiln.changelog` no longer deletes a changelog entry that is not written as a `- ` bullet (#2732).** Every section but Upgrade notes, Breaking and Known issues is read as `- ` bullets with two-space-indented continuation lines, and anything else was skipped without a word. An entry written as a paragraph, with `* ` bullets, or with a continuation line that was not indented counted as no entry at all, so `--check` passed it (no line cap, no link needed), and `--condense` then rewrote `CHANGELOG.md` without that text and archived none of it.
  - **What `--check` says now.** It fails on any non-blank line in such a section that belongs to no entry, naming the release, the section and each line by its line number in `CHANGELOG.md`, with the fix: start the entry with `- ` and indent its continuation lines by two spaces. This covers released sections too, since `--condense` rewrites those as well.
  - **What `--condense` does now.** It prints the same report and stops before writing anything.
  - **Unchanged.** Upgrade notes, Breaking, Known issues and a release's opening paragraphs are prose and keep every line, as before. The real `CHANGELOG.md` already passes.


<a id="runtime-integer-env-vars"></a>

- **Four numeric variables no longer crash boot on a value they cannot read (#2728).** `PORT`, `POOL_SIZE`, `SMTP_PORT` and `S3_ENDPOINT_PORT` were read with a bare `String.to_integer`, so `PORT=` (what compose passes through for a variable the host never set), `POOL_SIZE=" 20"` or `SMTP_PORT=587/tcp` stopped the release with an `ArgumentError` before anything else ran. They now go through `KilnCMS.Config.Env`, the reader every other numeric variable uses.
  - **What each value does now.** Surrounding whitespace is trimmed, so `" 4000 "` is 4000. Blank is the same as unset and keeps the default silently: 4000, 10, 587 and 443. Anything else keeps the default and warns on stderr, and the warning is replayed through `Logger` and Sentry once the system is up.
  - **Ports are bounded.** The three ports accept 1 to 65535; a value outside that range, such as `PORT=80800`, keeps the default and warns rather than failing inside the listener. `POOL_SIZE` accepts any positive integer up to 2147483647; `0` keeps 10 and warns.
  - **No migration; rolling the pin back is safe.** An older release crashes on the same values again.



<a id="direct-upload-cleanup-claim"></a>

- **A direct-upload completion holds off its staging cleanup until it is done (#2724).** `POST /api/media/uploads` queues `KilnCMS.Media.StagedUploadCleanup` to delete the staged object a minute after the token expires. A completion sent near the end of the token's hour, for a file whose copy down from the bucket took longer than that minute, had the object deleted under it; the truncated copy failed the byte sniff and the client got `415 unsupported_media_type`. Two completions of the same token at the same time could do the same to each other: each deleted the object when it finished, whatever the other was still reading.
  - **What happens now.** A completion first claims the cleanup job (`KilnCMS.Media.StagedUploadClaim`): one compare-and-set `UPDATE` of its `oban_jobs` row records a claim in `meta` and moves `scheduled_at` out by a 300-second lease, which a heartbeat renews every 60 seconds until the completion has finished. The job isn't due while the lease holds, so the delete can't run mid-copy however long the copy, the metadata strip and the variants take. When the completion has consumed the object it makes the job due at once; the job deletes again, which retries a staged-object delete that failed.
  - **One completion per token.** Only one completion can claim the job, so a concurrent second completion answers `422 not_uploaded`, and one item is created. A completion sent before the client's `PUT` landed finds nothing, gives the claim back and leaves the token usable, as before.
  - **A lost claim.** If the heartbeat stalls past the lease (the database unreachable for minutes) and the job runs, the completion stores nothing and answers `502 storage_failed`, "The upload was interrupted before it could be stored. Start it again with POST /api/media/uploads." The token is spent. A completion whose node dies leaves its lease to lapse, and the job then deletes the object.
  - **Issuing an upload.** `POST /api/media/uploads` now answers `502 storage_failed` when the cleanup job can't be queued (it used to log a warning and issue the upload anyway), since completing needs the job. Retry.
  - **For library callers.** `KilnCMS.Media.StagedUploadCleanup.schedule/4` returns `{:error, reason}` instead of `:ok` when the job can't be inserted; `KilnCMS.Media.DirectUpload.begin/3` returns `{:error, :storage_failed}` then, and `complete/4` can return `{:error, :claim_lost}`. The lease and heartbeat are `config :kiln_cms, KilnCMS.Media.StagedUploadClaim, lease_ms: 300_000, heartbeat_ms: 60_000`, there for tests to shorten. `docs/media-pipeline.md` ("Direct uploads") has the full lifecycle.
  - **No migration; rolling the pin back is safe.** See the [upgrade note](#direct-upload-claim-upgrade) for rolling deploys.




<a id="gen-content-plural"></a>

- **`mix kiln.gen.content` writes an irregular plural into the resource it generates (#2731).** `--plural` (and the plural `--from` takes from a dynamic type's `path_segment`) named the domain's code interfaces and the printed notices, but the generated `use KilnCMS.CMS.Content, type: :story` line had no `plural:`, so the macro fell back to `"<type>s"`. `mix kiln.gen.content Story --plural stories` gave the domain `list_stories` and `search_stories` and promised `/stories/<slug>`, while the resource registered `storys`: its JSON:API routes and public pages lived under `/storys`, and anything dispatching by the registered plural looked for a `list_storys` that was never generated.
  - **What the generator writes now.** When the plural differs from `"<type>s"`, the `use` line carries it: `use KilnCMS.CMS.Content, type: :story, plural: "stories"`. A regular plural (`Product`, or `--plural products`) is left implicit, so the line is unchanged for those.
  - **Promoting a dynamic type.** `--from` a type whose `path_segment` is `stories` now generates a resource that serves at `/stories`, so its public URLs stay where they were. A segment that can't name functions (one with a hyphen) still falls back to `"<type>s"`, and the promotion notice still says the URLs move.
  - **The notice's Tag hint names the right aggregate.** It suggested `count :storie_count` for `stories`, by trimming an `s`; it now says `count :story_count`, after the type, as `Tag` names its own counts.
  - **Not changed: the table.** The table name still defaults to `"<type>s"` (`storys`); `--plural` never set it, and the notice's `search_vector` migration still names that table. Pass `table:` by hand before the first migration if you want another name.
  - **Types you generated already.** A resource generated with an irregular `--plural` before this release still registers `"<type>s"`. Add `plural: "stories"` to its `use` line to make it match its interfaces; that moves its JSON:API base route and public URLs from `/storys` to `/stories`, so redirect the old paths if anything links to them. No migration.


<a id="migrations-check-follows-helpers"></a>

- **`mix kiln.migrations.check` reads the code `up` and `change` reach, not only the code written inside them (#2736).** The expand/contract gate judged the statements lexically inside `def up`/`def change` and nothing else, and read an `execute` argument only when it was a string literal. A `drop table` moved into a `defp` that `up` calls, `execute(fn -> repo().query!("ALTER TABLE posts DROP COLUMN slug") end)` and `execute("ALTER ..." <> x)` all passed as "none breaks the running release", and the reporting-view pin rule missed them too.
  - **What is followed now.** Every function of the migration module that `up`/`change` reaches, called directly, through other functions, through `__MODULE__.f()` or through a capture (`&drop_one/1`, `execute(&add_fkey/0)`), is judged as part of the forward direction. Each is read once, so recursion and cycles end. A finding points at the line in the helper, and a marker goes above the statement there. Only the forward half of `execute/2` is followed. The reporting-view rule follows `down`'s calls the same way, and a view dropped by a function called before the change counts.
  - **More SQL is read.** `repo().query!` and `Ecto.Adapters.SQL.query!` are judged like `execute`, inside an `execute` closure too. `execute(@backfill)` reads the attribute, `<>` of literals reads as one string, and a module function that returns a literal is read through. Interpolated SQL is read as before.
  - **What fails closed.** Forward code the check cannot read is a new `unanalyzable` finding: SQL built at run time (`execute(sql)`, `"ALTER ..." <> x`, `execute_file`), a call into another module (an app module, `Oban.Migration`, `Code.eval_string`), `apply`, a function held in a variable, and `use`/`import` of a module other than `Ecto.Migration`. Standard-library modules that never reach the database and the repo's data functions (`repo().update_all`) pass. Write the statement out, or excuse it with a `kiln:contract-ok` marker whose reason says what the code changes; see `docs/releasing.md`, "The check".
  - **Existing migrations.** Only added migrations are judged, so nothing already merged is affected. Over the whole history, `--all` reports five more findings than before, all opaque calls: `Oban.Migration.up`, three app-module backfills and one overlay `import`. No earlier finding went away.



<a id="s3-part-deadline"></a>

- **A large upload reaches S3 on a slow uplink (#2725).** An object over 16 MB goes up as a multipart upload in 5 MB parts, four at a time, and each part had 30 seconds, after which it was killed and the whole upload aborted with `{:error, :timeout}`. Under about 5 Mbit/s of uplink no part could finish in that time, so no such file could be stored at all, however long the caller would wait: a large video upload failed, and an `AVStripWorker` promotion retried and failed the same way.
  - **What happens now.** Each attempt at a part has as long as its size takes at a minimum throughput, `S3_UPLOAD_MIN_BYTES_PER_SECOND` (default 32768 bytes per second per part, which suits an uplink of about 1 Mbit/s or more), and never less than 30 seconds: 160 seconds for a full 5 MB part at the default. A connection that goes silent is still cut by the S3 client's 30-second receive timeout, and ExAws still retries that, a transport error and a `5xx` on its own.
  - **Retries.** A part that runs out of time, or still answers a `5xx` or a transport error once ExAws has given up, is sent again, up to three attempts in all, one second and then two apart, and each retry is logged as a warning. A `4xx` fails the part at once. A part that fails every attempt fails the store with its error, and the upload is aborted (`AbortMultipartUpload`) as before.
  - **Configuration.** `config :kiln_cms, KilnCMS.Storage.S3` takes `part_min_bytes_per_second`, `part_min_timeout_ms`, `part_attempts` and `part_retry_backoff_ms`; only the first has an environment variable. Concurrency stays at four parts.
  - **Still bounded elsewhere.** `AVStripWorker` gives a strip, upload included, 10 minutes, so a promotion of a file larger than about 10 minutes of uplink still fails and retries.
  - **No migration; rolling the pin back is safe.** An older release goes back to 30 seconds per part.








<a id="staging-script-guards-drop"></a>

- **`scripts/staging.sh down` and `up` check the database they act on, and act on the server `STAGING_DATABASE_URL` names (#2722).** `down` ran `dropdb <name>` against libpq's default server (`PGHOST`, the local socket, the current user), whatever host the URL named, and checked no name, although the script's header promised the name "must look ephemeral". `up`'s `createdb`, and the drop that cleans up an unscrubbed clone after a failed migrate or scrub, did the same: `up` could create the database on one server and copy production into another, and its cleanup could drop a same-named database on the default server.
  - **A name check before anything is created or dropped.** `up` and `down` refuse a database whose name lacks `staging`, `preview`, `ephemeral`, `tmp` or `scratch` (any case, percent-decoded as libpq reads it), the list the scrub already checked. A refusal ends with `Nothing was dropped` or `Nothing was created or copied`. `up` checks before its `mix` preflight, so nothing runs.
  - **`KILN_STAGING_FORCE` overrides it.** The script still never sets it, but now reads it for `up` and `down`, spelled as the app reads a flag: `true`, `1`, `yes` or `on`, any case, trimmed. Exported for `up`, it also reaches the scrub `up` runs, as it did before.
  - **A URL is required.** For `up` and `down`, `STAGING_DATABASE_URL` must be a `postgres://`, `postgresql://` or `ecto://` URL with the database in its path and no `dbname` in its query (which libpq would connect to instead). A passwordless `key=value` string or a bare database name was accepted before and is now refused, because the name it points at can't be checked. `scrub` is unchanged.
  - **The URL's server.** `createdb` and `dropdb` connect to the URL's host, port and user, with its TLS settings, through its `postgres` database and then `template1` if that fails. The password reaches them as `PGPASSWORD` only. When both attempts fail, the script prints each one's error: `up` carries on, assuming the database exists, `down` stops with `could not drop <name> on the server in STAGING_DATABASE_URL`.
  - **If you relied on the old behavior.** A `down` whose URL named one server while you meant the default one now drops on the URL's server. Check `STAGING_DATABASE_URL` names the server the clone is on.
  - **`scripts/restore.sh` still uses the default server** for its `createdb` and its drill's `dropdb` hint, and its drill's name check is case-sensitive; that is [#3329](https://github.com/The-Verscienta/kiln_cms/issues/3329).
  - **No migration; rolling the pin back is safe.** An older checkout's script drops on the default server again. See `docs/staging-environments.md` ("What `up` and `down` check before they create or drop").

<a id="webhook-failure-atomic"></a>

- **An exhausted webhook delivery is counted on the endpoint as it is in the database, not on the delivery job's copy (#2737).** `:record_delivery_failure` wrote `consecutive_failures + 1` taken from the endpoint the job read before its POST. If another delivery to the same endpoint got through in between and reset the count to 0, a job that had read the endpoint one failure short of the threshold still wrote the threshold, switched a healthy endpoint off and stamped `auto_disabled_at`. Two jobs exhausting at once wrote the same number, so one failure was lost. `:record_delivery_success` already decided on the row; the failure path now does too.
  - **What the action does now.** One `UPDATE` adds one to `consecutive_failures` and switches the endpoint off (`active: false`, `auto_disabled_at` stamped) when the new count reaches `KilnCMS.Webhooks.auto_disable_after/0`, all decided from the row's current values. An endpoint that is no longer active when the update runs (auto-disabled by a concurrent failure, or switched off since the job read it) is left as it is, matching the success path.
  - **Alerts fire once.** The record the action returns carries `:auto_disabled` metadata, true only for the update that switched the endpoint off. The admins' "webhook switched off" notice and email (`KilnCMS.Webhooks.HealthNotice`) and the security `alerts_silenced` notice (`webhook_auto_disabled`) both read it, so a second job finishing against an endpoint already off raises neither. The "webhook is failing" notice is raised for the failure that leaves an active endpoint at a count of 1. `HealthNotice.event_for/1` and `surface/1` now take only the returned record.
  - **No migration; rolling the pin back is safe.** An older release counts on the job's copy again.

<a id="announce-unique-executing"></a>

- **An edit that lands while the previous `Update` is fanning out is federated too (#2757).** `KilnCMS.Federation.AnnounceWorker` is unique on `{org_id, document_id, verb}` for 60 seconds, and that uniqueness counted jobs in `:executing`. An executing job has already read the document, so an `Update` enqueued for a second edit in that window was dropped as a duplicate of a job that would send the older content, and followers kept it.
  - **What is deduplicated now.** Only jobs that have not read the row yet: `:scheduled`, `:available`, `:retryable` and `:suspended`. Each of those reads the live record when it runs, so collapsing a duplicate into it still sends the latest content. A job that is executing or has completed no longer blocks a new one. `:completed` was never in the list.
  - **No migration; rolling the pin back is safe.** An older release drops the second `Update` again.



<a id="links-backfill-multiple"></a>

- **`mix kiln.links.backfill` keeps and rewrites the edges of list reference fields, and keeps the edges of references inside groups and flexible items (#2742).** The backfill writes a `content_links` edge for each stored `:reference` value and deletes the edges no value holds. It was written in 1.1, when a reference was a single object, and never learned the list shape that 1.5.0 added (`multiple: true`): it wrote nothing for a list and its prune, reading `custom_fields -> field ->> 'id'`, found no id in one, so it deleted every edge of every list reference field. 1.12.1 added edges for references inside group rows and flexible items, keyed by a dotted path such as `visits.doctor`; the prune found no key by that name and deleted those too. The data migration that runs the backfill on the upgrade to 1.1 lost nothing, since no install had list or nested values before then. If you ran it by hand on 1.5.0 to 1.12.1, see the [upgrade note](#links-backfill-multiple-upgrade).
  - **What it writes now.** The edges a save would write for a top-level reference field: an object is one edge at position 0, a list one edge per element at the element's index in the stored list (`[a, "junk", b]` gives `a` at 0 and `b` at 2), with the element's `link` object as the edge's link values. An element counts only when its `id` is a uuid. A target named twice in one list is one edge, at its last place, as a save keeps it. The shape is read from the stored value, not from the field's `multiple` setting, so a value stored before the field was switched between single and list is read as what it is.
  - **Realign.** An edge whose position or link values disagree with the stored value is rewritten to match, and the output counts these: `Reference links: N written, M realigned, K removed.` (was `N written, K removed`). `KilnCMS.CMS.ContentLinks.Backfill.run/1` returns `%{inserted:, updated:, deleted:}`; `updated` is new. A save landing mid-run can be realigned to what its value held when the run read it, until that record's next changing save, so run it in a quiet period.
  - **The prune keeps more.** An edge stays while its source still holds its target under its field, as an object or in a list. A nested edge (a dotted field path) stays while its source record exists. The backfill does not write or realign nested edges: a record's next changing save does, and a backfill for them is [#3357](https://github.com/The-Verscienta/kiln_cms/issues/3357).
  - **Smaller fixes on the way.** An id stored in upper case lost its edge on every run (inserted, then pruned as a mismatch against the lower-case uuid column); ids now compare in any case. A target named twice in a list kept an arbitrary place. A `link` that was not an object was copied onto the edge; it is now `{}`, as a save writes it.
  - **Known differences from a save.** When a value names no `type`, the backfill takes the field's `target_type` and ignores `target_types` (a later column the 1.1 migration's schema doesn't have); realign leaves `target_type` alone. A string id of exactly 16 bytes, which a save accepts as a raw uuid, is ignored here, and the prune deletes its edge (#3356). A record's next changing save settles both. The backfill does not check `max_sources`.
  - **No migration; rolling the pin back is safe.**




<a id="health-sweep-every-record"></a>

- **The daily health sweep reaches every overdue and expired record (#2738).** `KilnCMS.CMS.HealthSweep` read at most 500 stale records per content type, in no particular order. Raising an event does not change a record's `health`, and a `:create_task` reaction leaves the record overdue, so each run got the same 500 back: on a type with more, the rest never got a `<type>.health_overdue` or `<type>.health_expired` event, or the task a rule makes from it. Only a log line said so.
  - **It pages now.** The sweep reads 500 records at a time in `id` order and continues after the last one it saw, until a page comes back short, dispatching each page before reading the next. A sort alone would not have helped: nothing the sweep does takes a record out of the filter, so the same first page would come back every run.
  - **Telemetry counts every record.** `[:kiln_cms, :lifecycle, :health_sweep]` was capped at 500 per type with the read; its `overdue` and `expired` counts are now the full totals. It is emitted after the events are dispatched rather than before.
  - **More events on a large backlog.** A site with thousands of stale records of one type now gets an event, and so an `Automation.DispatchWorker` job, for each of them every day. A rule's `:create_task` stays one open task per record, as before.
  - **No migration; rolling the pin back is safe.** An older release goes back to the first 500 per type.


<a id="in-context-editor-locale"></a>

- **The in-context editor opens the locale variant it was linked from (#2758).** The editor at `/editor/site/<type>/<slug>` finds its record by slug and `?locale=`, and an absent locale meant the default one. Both links into it from the content editor, the toolbar's "Visual" button and each preview block's "Edit", left the locale out. On a `fr` variant whose slug its `en` source shares, they opened the English record, and every inline edit, reorder and autosave was written there. With different slugs they answered "No such content to edit."
  - **What the links carry now.** `?locale=<the record's locale>`, alongside `focus=` on a block link. The route stays keyed on slug and locale rather than record id, because the visual-editing bridge (`priv/static/bridge.js`) and its stega payloads already address the editor that way and send the locale.
  - **An absent locale is no longer a guess.** A URL without `?locale=` (a hand-typed one, or an older bridge) still opens the default-locale record when that is the only variant of the slug you can read. When the slug has variants in more than one locale, the editor sends you back to `/editor` with "This content exists in more than one language" instead of picking the default.
  - **No migration; rolling the pin back is safe.** An older release opens the default-locale variant again.

<a id="presentation-edit-after-save"></a>

- **The Presentation console's edit pane keeps the saved text after a Save (#2759).** Save rebuilds the open text or rich-text region so the next edit starts from what was stored, but it rebuilt it from a copy of the block taken when the pane was opened. The region showed the text from before the save, and because the region's script sends its whole text whenever typing pauses, one more character put the old text back, and the next Save wrote it over the edit just saved.
  - **What happens now.** After a Save the pane is re-read from the saved record: a text or rich-text block shows its stored value and stays open for more typing, and a title or excerpt input shows the saved value. A failed or conflicting Save leaves the pane as it was; Reload still closes it.
  - **No migration; rolling the pin back is safe.** An older release shows the pre-save text again.

<a id="organize-stale-run"></a>

- **Organize's tag review no longer shows a run for the wrong selection (#2762).** Changing the Type, State or Untagged filter on `/editor/organize?tab=tagging` while **Propose tags** was running cleared the run and re-enabled the buttons, but the run kept going. When it finished, its proposals appeared as the run for the new selection, rows for documents the filter no longer selected among them. Because the buttons were enabled again, a second Propose or Index tag names could start beside the first and spend the embedding budget a second time.
  - **What happens now.** Each run carries the selection it was started for. A run that finishes after the filter changed is set aside, with a note to propose again for this selection, and its rows are never shown. **Proposing…** and **Indexing…** stay on until the task in flight finishes, so a second run cannot start beside it. A tab load that finishes after the filter changed is dropped the same way.
  - **No migration; rolling the pin back is safe.** An older release shows the stale run again.




<a id="rename-rewrites-working-copies"></a>

- **A field rename, delete or reshape now reaches the drafts of live records (#2744).** Renaming a custom field moves its stored values to the new key, deleting one purges them, and flipping `multiple` reshapes them, in one statement over the type's table. That statement rewrote the live `custom_fields` column only. A live record's pending working copy holds its own copy of the map (in `working_fields`), with a fingerprint of the live map it was saved against (`working_base`), and neither was touched. So after an admin renamed `subtitle` to `tagline`:
  - *Publish changes* reported a conflict on *Custom fields* that nobody made, because the live map no longer matched the draft's recorded base. *Use mine* then published the draft's map with the old key, which no definition declares any more, so the draft's value was dropped.
  - A release holding that record was blocked (*Live page changed since the draft*), and an unpublish or archive kept the live custom fields and dropped the draft's custom-field edits.
  - The same happened for a link field (a reference's `"link"` values), a group sub-field, a flexible item's sub-field or `_settings` key, an item type rename or delete with `purge_items?: true`, and a `multiple` flip (held lists included).

  **What it does now.** One `UPDATE` rewrites both the live map and the draft's map of each row with the same SQL, so the two cannot disagree. A key only the draft holds is rewritten too. The draft's base moves with the rewrite: a base that matched the draft still matches it, one that matched the live map matches the rewritten live map, and a base that already disagreed with both is left alone, so a conflict somebody really made is still reported (and *Use mine* now keeps the value under its new key). A draft the rewrite leaves equal to the live map stops holding custom fields, but stays listed as pending until it is published or discarded. Versions are not rewritten: they are hash-chained. `KilnCMS.CMS.Changes.SyncFieldValues` documents the details under "Working copies"; the new `KilnCMS.CMS.WorkingCopy.rebase/5` moves the base.

  **Affected releases.** Top-level rename and delete since 1.0.0; reshape and link fields since 1.5.0; group sub-fields since 1.6.0; flexible items since 1.11.0; held lists since 1.12.0; all through 1.12.1. What to do about drafts and values from those releases is in [Upgrade notes](#rename-rewrites-working-copies-upgrade).

  **One-time effects after a rename or delete.** Every rewritten row's `lock_version` moves, unlike the other background writers (oEmbed resolves, media re-snapshots, `mix kiln.fields.convert`, the event sweep). This write changes which keys a form loaded earlier would save back, so a stale save must be refused rather than restore the old key. In practice:
  - An editor who had an affected record open sees *This content changed elsewhere. Reload to get the latest before saving.* on the next save or autosave. **Reload latest** picks up the renamed field with the draft's value.
  - A JSON:API client that sends `If-Match` with a tag read before the rename gets one `412 precondition_failed`. Re-read the record and retry.
  - A release go-live that read its records before the rename fails as stale. **Reopen for editing** and publish it again.
  - `updated_at`, versions, firing and webhooks are left alone, as before.

  **Delete guards count drafts too.** A value or item that only a draft holds is now data for every check that asks "would this delete lose something": `mix kiln.fields.import` (and the console's **Sync definitions from a file**) blocks a delete, retype or narrowing on it without `--allow-data-loss`; an item type with items only in a draft can't be deleted without `purge_items?: true`; and the item count on the fields screen's delete confirmation includes them (a record counts the larger of its live and draft items).

  **Failures.** On its own, the rewrite runs after the definition change has committed. If the combined rewrite fails, it is logged and the live values are moved alone, as before this fix, leaving the drafts in their old shape. Inside a transaction a caller opened (`mix kiln.join.retire`, a field-sync import, an item type's own delete with `purge_items?`), a failure is returned as the action's error and the whole operation rolls back.
  - **No migration; rolling the pin back is safe.** An older release reads the rewritten drafts as ordinary drafts; its own renames go back to rewriting the live map only.
